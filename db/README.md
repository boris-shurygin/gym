# YDB, транзакции и миграции

P03.2.2: базовое подключение SQLAlchemy и служебная схема проверены на настоящей staging YDB. P06 добавляет additive-миграцию `0002_accounts_programs` и [пять прикладных таблиц](../infra/accounts-programs.md) для входа и программ; реальное подключение OAuth/ACL сверяй с журналом. При настроенном входе HTTP-функция открывает YDB для прикладных транзакций, но не выполняет DDL. Сервер занятий и синхронизации остаётся P07/P08.

## Локальная одноразовая база

Нужны Docker с Linux-контейнерами, x86_64 и Python 3.12. В текущем Windows-окружении Docker/WSL отсутствуют; вместо локальной имитации при разработке использованы отдельные синтетические таблицы staging. Это не разрешает подключать PR к облачной базе: CI запускает собственный контейнер.

```powershell
docker run --rm -d --name gym-ydb --hostname localhost -p 127.0.0.1:2136:2136 ydbplatform/local-ydb@sha256:9e46fd45875551a75bcf34d0bb9ca0baa1d8763a4ccf2070af45f4467c4b7402
py -3.12 -m venv .local/backend-venv
& ./.local/backend-venv/Scripts/python.exe -m pip install -r db/requirements.txt
$env:GYM_YDB_ENDPOINT = 'grpc://127.0.0.1:2136'
$env:GYM_YDB_DATABASE = '/local'
$env:GYM_YDB_AUTH = 'anonymous'
```

Дождись состояния `healthy` в `docker inspect gym-ydb`, затем:

```powershell
& ./.local/backend-venv/Scripts/python.exe -m unittest discover -s tests/ydb -p 'test_*.py' -v
& ./.local/backend-venv/Scripts/python.exe -m db.migrate --job-id local-initial
& ./.local/backend-venv/Scripts/python.exe -m db.migrate --job-id local-initial
docker stop gym-ydb
```

Второй вызов миграции возвращает прежний успех с `replayed: true` после проверки фактической схемы. В Linux используй `python3 -m venv` и `.local/backend-venv/bin/python`; переменные задай через `export`.

Контейнер — официальный local-ydb 26.2.1.14 с закреплённым digest. Данные одноразовые, порты привязаны к loopback. В CI тот же образ получает отдельный экземпляр на каждом job, без облачных токенов. Недоступная YDB приводит к ошибке тестов; моки/SQLite/skip не заменяют интеграцию.

## Подключение и границы транзакции

`api.database.DatabaseSettings` принимает отдельные endpoint, абсолютный путь базы и способ доступа: `anonymous`, `metadata` либо временный `token`. Без TLS/авторизации разрешён только loopback. IAM-токен передаётся в `create_engine(..., token=...)` отдельно от URL; файлы ключей/секреты в Git не нужны. Для будущей облачной функции предусмотрены `MetadataUrlCredentials` её сервисного аккаунта. В P04.2.1 [точечные права staging](../infra/ydb-access.md) применены и проверены под временными токенами: API получает DML только на разрешённой таблице, DDL/GRANT и служебные данные закрыты; CI без DML/DDL. Metadata-аутентификация развёрнутого runtime проверяется далее.

Закреплены SQLAlchemy 2.0.55, ydb-sqlalchemy/ydb-dbapi 0.1.24 и YDB SDK 3.33.2 с транзитивными зависимостями. По умолчанию dialect использует autocommit, поэтому фабрика явно применяет `SERIALIZABLE` при каждом подключении через `OptionEngine`. Этот публичный механизм также обходит ошибку сброса isolation level при переключении на DDL в выбранной версии dialect.

`transaction(engine, callback)` начинает новую транзакцию и повторяет **весь callback только после `ydb.Aborted`**, максимум четыре попытки по умолчанию. У callback не должно быть внешних побочных действий. Неопределённый результат commit/сетевая ошибка не запускают повтор автоматически: вызывающий прикладной сервис должен разрешить такой исход через свой неизменяемый ID и квитанцию. Эти сервисы появятся в P06/P07.

## Миграции

`Migrator` работает отдельно от HTTP. Начальная ревизия `0001_runtime_metadata` создаёт только служебную таблицу `runtime_metadata(key, value)`. Полная модель пользователей/тренировок не утверждается этой таблицей. Административные таблицы блокировки и заданий создаются перед Alembic; версия схемы хранится в отдельной таблице Alembic со строковым PK без autoincrement.

Порядок работы:

1. Создай/проверь административные таблицы, затем атомарно захвати блокировку в YDB.
2. Проверь `job_id`, целевую ревизию и checksum миграций. Повтор прежнего ID с другим содержимым отклони.
3. Отметь задание `running`. Выполни аддитивные DDL вне DML-транзакции; существующие таблицы проверь, не считай их наличие успехом.
4. Перед записью ревизии проверь набор столбцов, точные YDB-типы, nullable и порядок PK. Обычная reflection dialect объединяет Int32/Int64; проверка использует точный describe того же DBAPI.
5. Отметь `succeeded` только после проверки схемы и ревизии. При ошибке сохрани `failed`; следующий вызов с тем же `job_id` может продолжить после исправления. Освободи свою блокировку.

Несколько DDL не откатываются общей транзакцией. Частично созданная правильная таблица не мешает повтору, а расхождение схемы останавливает миграцию без отметки ревизии. Автоматического `downgrade` нет. Блокировка **не перехватывается по таймеру**: после аварийного завершения процесса она требует административного восстановления с подтверждением, что старый исполнитель остановлен. В P04.2.2 [приватный Serverless Container](../infra/migration-worker.md) проверен на staging: он использует внешнюю блокировку, поколения, checkpoint и отдельный recovery-режим. После неясного шага сохраняет lease для администратора; обычный запрос не включает recovery. Локальный CLI остаётся только для одноразовой локальной БД и не является production-исполнителем. Промышленный gate/выпуск проверяются в P05.

## Фактические проверки

На staging проверены настоящие DML/DDL и транзакции: типы/Unicode/NULL/время, атомарность двух таблиц, повтор операции с квитанцией, конфликт двух соединений и повтор после abort. Потеря подтверждения commit моделируется после **реального commit**; callback не повторяется, запись действительно существует.

Проверены миграции пустой и частично созданной схемы, повтор задания, сохранение существующих данных, запрет параллельного исполнителя, отклонение неправильной схемы/ширины чисел и другого checksum. Наборы таблиц получают случайный префикс данного процесса и удаляются после прогона; имена чужих таблиц не используются. Для staging DDL ограничен по частоте, чтобы очистка укладывалась в квоту Serverless. После успешного прогона база снова пуста.

Это проверка базовых семантик хранения, не готовая авторизация или синхронизация Gym. Docker-вариант и Linux job отдельно проверяются в GitHub после публикации PR. Пакет функции и результаты проверки runtime описаны в [api/README.md](../api/README.md).
