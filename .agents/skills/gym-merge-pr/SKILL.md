# Слить PR Gym

Прочитай [процесс разработки](../../../docs/development-workflow.md), применимые AGENTS.md, [план](../../../docs/development-plan.md), [журнал](../../../docs/development-log.md) и [CI/CD](../../../docs/ci-cd.md).

1. Выбери PR: явная ссылка/номер, иначе PR текущего этапа из журнала с проверкой GitHub. При запросе «последний» ищи последний PR этой работы в этом репозитории. Уточни выбор только при действительной неоднозначности.
2. Проверь репозиторий, base main, head SHA, diff, состояние Draft, mergeability, обязательные проверки и необходимые ревью. Изучи изменения после прежнего просмотра. Не обходи защиты ветки или неуспешный CI.
3. Если PR уже слит, переходи к обновлению локального состояния. Иначе слей его разрешённым способом, проверяя ожидаемый head SHA при операции merge. Команда пользователя уже разрешает это слияние, второе разговорное подтверждение не нужно. При конфликте не делай автоматический force/admin merge; сообщи, какое исправление требуется.
4. Получи подтверждение merge и SHA. Обнови origin/main и локальный main только fast-forward. Сохрани незакоммиченные правки и опубликованную историю; если рабочая копия занята, следуй варианту из процесса и явно назови реально обновлённую копию/ref. Не удаляй ветки автоматически.
5. Для прикладного изменения используй `python -m infra.delivery_status --sha <merge-SHA> --wait`: команда ограниченно ждёт main CI/staging и один раз сверяет публичную идентичность выпуска. Успешного CI deploy и совпавшего release ID достаточно: deploy уже проверяет байты, API, Gateway, приватность и auth smoke. После этого сразу переходи к итоговой сводке. Не запускай повторную полную сверку артефактов/облака или новый браузерный сценарий для каждой кнопки. Дополнительная диагностика нужна при сбое, явном требовании приёмки или изменении механизма деплоя. Если детектор дал `deploy=false`, приложение не выкатывается и ждать staging не нужно. Не называй успешный merge успешным деплоем.
6. Кратко обнови журнал: PR/merge SHA, CI/staging run, release ID, результат и следующий пункт. Не создавай отдельные скрипты записи отчётов или коммит в main ради постфактум-метаданных; включи их в следующий содержательный PR. Не расширяй обычную UI-полировку в повторную приёмку всего этапа.

Предпочитай коннектор GitHub, а недостающие операции выполняй доступным Git/CLI. Если внешняя операция недоступна, не подменяй её записью в журнале.

Сообщи PR/merge SHA, состояние локального main и престейбла. При отдельной команде merge заверши работу на этом. В автономном режиме продолжи следующий этап только внутри ранее разрешённого списка/диапазона по [gym-next-stage](../gym-next-stage/SKILL.md), без повторного подтверждения. Production выполняй по [gym-deploy-stable](../gym-deploy-stable/SKILL.md) только при явном разрешении на выпуск, в том числе данном в исходном запросе.
