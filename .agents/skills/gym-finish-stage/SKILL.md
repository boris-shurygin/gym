# Завершить этап и подготовить PR

Прочитай [процесс разработки](../../../docs/development-workflow.md), применимые AGENTS.md, [план](../../../docs/development-plan.md), [журнал](../../../docs/development-log.md) и [CI/CD](../../../docs/ci-cd.md). Сверь критерии выбранного пункта с фактическим diff и замечаниями пользователя.

1. Определи текущий этап, ветку и существующий PR. Проверь изменения main доступным Git-инструментом. Если работа находится на main, подготовь отдельную ветку с сохранением правок; не коммить рабочий результат прямо в main.
2. Просмотри весь предлагаемый diff и отдели несвязанные изменения. Не используй безусловный `git add .`. Не включай секреты или чужую работу без основания в запросе/контексте.
3. Выполни предусмотренные локальные проверки изменённых компонентов и обязательные проверки проекта. Для документации проверь ссылки и `git diff --check`; для реализации используй фактические команды репозитория. Исправь относящиеся к этапу ошибки, повторив затронутые проверки.
4. Если критерий готовности не выполнен, дополни результат в границах этапа. Если обязательная проверка недоступна, явно зафиксируй ограничение; такой PR может быть только Draft, пока готовность не подтверждена. Не маскируй падающий тест как пропущенный.
5. Запиши результат и проверки в журнал до коммита. Подготовь содержательные коммиты выбранных файлов, опубликуй ветку без force push и создай PR в main. Предпочитай доступный коннектор GitHub; используй CLI, когда нужной операции нет. При отсутствии доступа оставь локальный результат готовым и назови конкретный блокер публикации.
6. В PR укажи этап, изменившееся поведение/документацию, проверки и ограничения. При повторном вызове обнови PR той же ветки вместо создания дубля. Состояние «PR открыт» и ссылку запиши после подтверждения GitHub; эти локальные метаданные можно включить в следующий содержательный коммит.

Команда завершения уже разрешает коммит, push и создание/обновление PR согласованного объёма; не проси повторного разрешения. Если опубликованная ветка изменилась неожиданно, сначала сверяй расхождение, а не перезаписывай её.

В конце сообщи ссылку на PR, результаты локальных проверок и текущий статус CI. Не выполняй merge и не переходи к следующему пункту автоматически.
