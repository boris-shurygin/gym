# Выпустить Gym в стейбл

Прочитай применимые AGENTS.md, [процесс разработки](../../../docs/development-workflow.md), [CI/CD](../../../docs/ci-cd.md), [план](../../../docs/development-plan.md), [журнал](../../../docs/development-log.md) и ADR-0011. Стейбл — production, престейбл — staging.

1. Проверь наличие настроенного production workflow и доступов. Если их нет, назови недостающий этап плана; не имитируй выпуск и не заменяй его прямыми командами к production с компьютера.
2. Выбери явно заданный выпуск, либо последний подходящий выпуск с успешным staging. Проверь main SHA, run сборки, неизменяемый манифест, доступность/хеши артефактов и успешные staging-тесты именно этого кандидата. Статус другого SHA, текущая вершина main или просто последний run не подходят. При неоднозначном выборе уточни release ID.
3. Сообщи пользователю выбранные release ID/SHA и основание готовности перед запуском. Команда деплоя разрешает выпуск этого однозначно выбранного кандидата; повторное разговорное одобрение не нужно. Не обходи обязательное одобрение GitHub Environment: если job его ждёт, сообщи ссылку на ожидающее действие.
4. Запусти предусмотренный CI/CD процесс продвижения с точным идентификатором выпуска. Предпочитай коннектор, если он поддерживает dispatch; иначе используй доступный авторизованный CLI/API. Не создавай вместо отсутствующей операции другое событие, например пустой push или новый тег.
5. Следуй порядку CI/CD: совместимые миграции внутри Yandex Cloud → версия API из проверенного пакета → PWA из проверенных ресурсов → smoke-тесты. Не пересобирай код и не запускай production-DDL на GitHub runner/локальном компьютере. Не меняй выпуск, пока текущая миграция/деплой не завершены.
6. Проверь фактический итог workflow и доступность нужной версии. При сбое зафиксируй частично выполненные шаги и останови продвижение; используй только предусмотренное восстановление/откат совместимых API/PWA, без автоматического downgrade БД. Перед повтором проверь состояние уже исполненной миграции; не запускай бесконечные повторы.
7. Запиши в журнал release ID, SHA, run, окружение, результат smoke-тестов и выполненное восстановление. При повторной команде для уже установленного выпуска проверь состояние вместо повторной миграции.

В конце сообщи установленную версию и ссылку на run либо точный статус ожидания/сбоя. Успешный запуск workflow ещё не является успешным выпуском.
