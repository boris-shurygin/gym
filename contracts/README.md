# Внешние контракты Gym v1 — P02.4.2

Обновлено: 2026-10-26. **Контракт P02.4.2 принят пользователем 2026-10-26 командой «норм, завершаем этап».** API/OAuth/YDB ещё предстоит реализовать. Основа — ADR-0014–0016; уточнения версий/транспортов/канонизации зафиксированы в принятом [ADR-0017](../docs/adr/0017-rest-mcp-contracts.md). Здесь есть исполняемые проверки схем и примеров; сервер, OAuth и транзакции YDB ещё не реализованы.

Редактируй источники `schema.json`, `bindings.json`, `errors.json`, затем пересобери производные файлы. OpenAPI/MCP записаны компактно: проверяй их по исходным DTO/привязкам и отсутствию расхождений, не правь вручную. В примерах `input` — полный прикладной DTO после сборки path/query/body, а не всегда буквальное HTTP-тело.

Из корня в текущем Windows-окружении:

```powershell
py -3.12 -m venv .local/contracts-venv
& ./.local/contracts-venv/Scripts/python.exe -m pip install -r contracts/requirements.txt
& ./.local/contracts-venv/Scripts/python.exe -m contracts.generate --check
& ./.local/contracts-venv/Scripts/python.exe -m unittest discover -s tests/contracts -p 'test_*.py' -v
node tests/contracts/canonical-vectors.mjs
```

Для пересборки используй `python -m contracts.generate` в этом окружении. В Linux команды `python` выполняются из соответствующего venv; Node берётся из [версии клиента](../web/.node-version). В Web checks отдельный job contracts проверяет схемы без облачных прав, web — lint, сборку, модульные тесты и два эталона Node. Браузерный job запускается только при изменениях `web/` (включая E2E-тесты) или `.github/workflows/ci.yml`; изменения только документации/контрактов его пропускают. Он использует официальный образ Playwright с готовыми браузерами, закреплённый по версии 1.64.1 и digest; при обновлении `@playwright/test` обновляй образ вместе с ним.

Формат DTO и поля ошибок проверяются настоящим JSON Schema-валидатором с явной проверкой даты/времени; локальные инварианты дополняют схему (уникальные ID, диапазоны, связи подходов). OpenAPI проверяется официальной [схемой документа 3.1](vendor/openapi-3.1.schema.json). Это не тест авторизации, сетевого Gateway или commit YDB.

## Версии и точные значения

Собственные ресурсы — `/api/v1/*`, `SyncOperation.schema_version = 1`. Поля закрыты (`additionalProperties: false`), тип `fixed` единственный. Отсутствующие nullable-поля не подразумеваются: например, у плановой цели `rep_min`/`rep_max` передаются явно как `null`, если диапазона нет. У GET-параметров допускается отсутствие: `limit` по умолчанию 30, период 30 дней, пояс из профиля (до выбора UTC).

Веса — целые граммы 0–2 000 000, повторения — целые 1–1 000, счётчики/ревизии — не более 2^53−1. Времена — RFC 3339 с обязательным смещением/Z и максимум шестью знаками долей секунды; календарная корректность проверяется. `Timezone` структурно ограничен строкой, а существование пояса проверяет сервер по IANA. Проценты/тоннаж не назначают новые цели; сводка не суммирует несопоставимые упражнения в «рост силы».

Технические пределы первого контракта: 20 шаблонов программы, 20 позиций упражнения в шаблоне, 30 целей позиции, 2 000 результатов занятия, страницы до 100 элементов. Это ограничения размера представления, не фиксированный каталог/набор тренировок. JSON-представление запроса или одного DTO/страницы ответа — до 1 MiB, глубина до 64. Сервер может уменьшить страницу до безопасного размера, сохраняя курсор, но не обрезать объект или выдать неполный отчёт за полный. Реальные пределы Gateway/runtime проверяются в P03.2/P04; при несовместимости уменьши лимит/разбей выдачу явным контрактом, не теряй очередь.

v1 не получает новые неизвестные строгому клиенту поля/типы молча. Для несовместимости нужен новый контракт и совместимый путь приёма сохранённых операций. Старый `schema_version = 1` не истекает по возрасту; при действительно неподдержанной версии возвращается `upgrade_required` без исполнения. Не изменяй содержание/ID старой операции под видом повтора. Примеры прежних проектных документов показывают смысл данных; точный wire-формат задаёт этот набор схем.

ID операции/устройства/занятия/результата — UUID v4; остальные ID — ограниченные непрозрачные строки из схемы. В v1 `session_exercise_id` копирует `template_exercise_id` выбранного снимка и определяется вместе с `workout_id`; общий `exercise_id` каталога не заменяет позицию. Тип правила закреплён контрактом как `fixed`, параметры — явные цели, версия построения плана — `fixed-v1`. Текущий `local-demo` и его `Command` не отправляются как v1 и не переносятся в аккаунт автоматически.

## HTTP и идентичность

Полная таблица маршрутов — в `bindings.json`/OpenAPI. Основные группы: `/auth/*`, профиль/каталог/программа/планы, `/workouts`, `/stats`, `/sync`, `/program/changes`, `/telemetry`.

REST использует серверную cookie `__Host-gym_session`; все личные ответы, ошибки и auth-перенаправления имеют `Cache-Control: no-store`. Для изменяющих cookie-запросов нужны точный Origin и `X-CSRF-Token`, связанный с текущей сессией. `/auth/logout` без действующей сессии может вернуть 204 повторно; при действующей нужны те же защиты. Отзыв MCP-grant — отдельное действие по ADR-0014.

Владелец просматривает `/api/v1/agent-grants` и отзывает выбранный grant через `/api/v1/agent-grants/{grant_id}/revoke`. Возвращается только метаинформация подключения, без access/refresh tokens. Отзыв идемпотентен, запрещает его серверный доступ и не удаляет историю/программу. Агенту эти операции не выдаются.

`GET /auth/login` по умолчанию возвращает в `/app` с назначением `login`; допустимые пути возврата перечислены в схеме, произвольные URL не принимаются. Callback получает code/state либо error/state; всё равно проверяет одноразовую браузерную транзакцию. Неприглашённая личность получает `not_invited`, без создания аккаунта с правами. Токен Яндекс ID не является токеном Gym.

Для GET собери DTO из однократно декодированных path/query. Повторённые/неизвестные query-поля отклоняются; целые параметры передаются десятичными цифрами, затем строго преобразуются к целому и проверяются схемой. Пропущенный параметр отличается от строки `null`. Для POST/PUT используй UTF-8 `application/json` без BOM; path-поля убраны из HTTP-тела OpenAPI и добавляются сервером к прикладному DTO. Их повтор в body не разрешает подмену пути. Пустой logout соответствует DTO `{}`.

Владельца определяй из аутентифицированного контекста. `expected_owner_id` — дополнительное проверяемое ожидание, не источник полномочий. Оно обязательно для создания занятия/черновика и других описанных изменений, чтобы поздний запрос прежнего профиля не создал данные в новом. Каждая ссылка на занятие/план/черновик проверяется на принадлежность; чужой ID возвращает `not_found`, без чужой квитанции. Ошибки/trace содержат безопасные коды, не токены, тексты результатов провайдера или stack trace.

## MCP и OAuth

`POST /mcp` — отдельный Streamable HTTP endpoint с токеном Gym для своего audience/окружения. Первый режим отвечает JSON без долгоживущих SSE/подписок; инструменты не требуют фонового соединения. Cookie PWA, IAM и токен Яндекс ID здесь не дают доступа. Предрегистрация клиента, PKCE S256, `resource`, scopes и отзыв следуют ADR-0014.

Маршруты OAuth-компонента: `/oauth/authorize`, `/oauth/token`, `/oauth/revoke`; discovery — `/.well-known/oauth-authorization-server` и `/.well-known/oauth-protected-resource/mcp`. Они используют стандартные OAuth/MCP формы/метаданные выбранной библиотеки, не собственный формат DTO Gym. Issuer, точные callback URI, клиентский метод и реально поддержанные версии протокола берутся из проверенной конфигурации окружения. Не объявляй работающими произвольные методы, DCR/CIMD или совместимость реального ChatGPT без испытания P06/P10.2. SDK должен корректно обрабатывать версию/метаданные MCP, включая отличия старых клиентов.

`mcp-tools.json` описывает аргументы/структурированный прикладной результат, а не весь JSON-RPC/OAuth-сервер. Для успешного вызова `structuredContent = {ok: true, data: DTO}`; для прикладной ошибки — `{ok: false, error: Error}` и `isError: true`. Текстовый блок содержит сериализованный безопасный результат; protocol-envelope формирует SDK выбранной версии. Ошибки JSON-RPC/метаданных остаются протокольными; HTTP 401/403 с challenge обрабатываются до инструмента. Не подменяй их успешным пустым ответом.

Публикуй список инструментов в стабильном порядке, фильтруя по выданным scopes. Hints/`_meta` манифеста не являются проверкой прав. Нет MCP-инструментов для записи подходов, телеметрии, выхода или создания одобрения. `program:draft` позволяет предложить/заменить/проверить свой черновик; `program:publish` — только применить уже существующее серверное одобрение. Каталог `list_exercises` нужен агенту для выбора реальных ID оборудования/упражнений вместо выдумывания ссылок.

## Канонизация, digest и повтор

Формат **Gym canonical-json-v1** реализован в `canonical.py` и закреплён эталонами Python/Node:

1. Отклони повторяющиеся ключи, невалидный UTF-8/Unicode, неизвестные поля по схеме, нецелые JSON-числа (включая `1.0`/`1e0`), NaN/Infinity и числа вне точного диапазона.
2. Проверь DTO и локальные инварианты. Не добавляй скрытые default-поля в канонические SyncOperation/Proposal: nullable-поля обязательны и явны. GET-defaults к этим хешам не относятся.
3. Имена полей ASCII сортируются лексикографически рекурсивно; порядок массивов сохраняется. Строки не нормализуются по Unicode, время не переводится в другой пояс. Используются JSON escaping управляющих символов, UTF-8 без BOM, без пробелов между элементами. `-0` после разбора — целое 0.
4. SHA-256 считается от префикса и канонических байтов: `gym:sync-operation:v1\n` для полного SyncOperation, `gym:program-change:v1\n` для полного Proposal (включая базовую версию/обоснование), `gym:request:v1\n` для `{operation_id: имя_сервиса, input: полный_DTO}` прочих идемпотентных записей. Здесь `\n` означает один байт LF.

Хеш не подтверждает пользователя или факт одобрения. Строки, отличающиеся составом Unicode или представлением времени, считаются разным содержанием. Не изменяй уже сохранённую операцию, переименовывая поля/переводя её время/склеивая последующие правки.

Sync-ключ — `(пользователь, operation_id)` по ADR-0015; все команды занятия сериализуются через точную ревизию либо успешную квитанцию предшественника. Для `start_workout` требуется ревизия 0, для других — существующая ревизия >=1 либо зависимость. `after_operation_id` не означает «любая текущая версия».

Тот же ID/содержание возвращает прежнюю квитанцию **до** повторной проверки старого предусловия. Другой контент — `operation_id_reused`. Применённая квитанция неизменна, даже если занятие уже исправлено; старый ответ не откатывает локальный экран/очередь. Окончательная ошибка корректной команды может иметь `RejectedReceipt`; неизвестная зависимость временная и не расходует операцию. GET квитанции с `not_found` не доказывает, что параллельный запрос не исполнится: исход выясняется тем же ID.

Создание/замена/публикация черновика и запись профиля используют отдельный журнал `(пользователь, request_id)` с привязкой имени операции и полного DTO, успешного/окончательно отклонённого результата. Проверки действующего аккаунта/гранта идут до возврата сохранённого личного результата. Неизвестный commit повторяется с тем же ID; исправление окончательно отклонённого содержимого — новый ID. Обе категории квитанций не удаляются коротким TTL.

## Черновик, одобрение и публикация

`propose_change` создаёт редакцию 1; `replace_change` требует текущую `expected_revision`, сохраняет новую редакцию и делает прежние проверки/одобрения непригодными. Черновик содержит полную предлагаемую программу, а не неявный merge-patch. Ссылки каталога и база проверяются сервером; устаревшая база создания/замены — `program_conflict`. Новая версия без исходной программы использует `base_program_version_id = null`, без особой роли «первого вошедшего».

`validate_change` не публикует: валидный по форме запрос возвращает `ValidationReport`, в том числе `valid: false` для семантических проблем/устаревшей базы. Ошибка ревизии самой редакции возвращается отдельно. Отчёт не заменяет повторную проверку в момент публикации.

Владелец через `approve-and-publish` подтверждает ID/редакцию/base/digest с действующей cookie, CSRF и проверкой личности не старше 10 минут. Сервис создаёт/связывает одобрение и публикует точную редакцию атомарно. Если черновик от агента, привязка к клиенту/grant определяется сервером; входное поле `approved` и произвольный переданный grant не принимаются.

Общий `publish_approved` проверяет владельца, редакцию, базу, digest, живой grant/права и одобрение на 10 минут/одно применение; создаёт неизменяемую версию и квитанцию атомарно. По основному UX кнопка Gym уже выполнила публикацию: последующий `apply_program_changes` с ID того же одобрения возвращает прежний результат без новой версии. Не добавляй выдачу неисполненного одобрения агенту отдельным неописанным endpoint; для другого UX нужно явное расширение контракта. Отзыв доступа не обходится чтением старой квитанции.

Новая программа не меняет снимки начатых/прошлых занятий. Редакция целей сама не исправляет фактические подходы; исправления истории сами не меняют текущие явные цели `fixed`.

## Дельта, ошибки, аналитика и диагностика

Курсор непрозрачен, связан с владельцем, версией/фильтрами и согласованной границей `H`. Страница изменений содержит неизменяемые версии, не плавающие указатели. `next_cursor` при `has_more: false` — checkpoint H следующего цикла. Страницу и курсор клиент сохраняет одной транзакцией, не удаляя ожидающие правки.

Bootstrap выдаёт программу/планы, активные и последние 30 завершённых занятий через неизменяемый манифест на 15 минут. `checkpoint_cursor` нельзя применять до полного сохранения всех страниц; незавершённая загрузка не заменяет старую базу/очередь. Истёкший манифест/курсор (`cursor_expired`) запускает bootstrap заново, а не очищает outbox. Журнал дельты 30 дней не является TTL квитанций/фактов.

`Error.action` отделён от `retryable`: 401 требует входа, конфликт — разбора, `upgrade_required` — совместимого обновления. Только `retry` автоматически повторяет исходные данные с задержкой; у 429 есть положительный `retry_after_seconds` и HTTP `Retry-After`. 503/потеря ответа не являются подтверждением отсутствия записи. Ошибки/квитанции чужого аккаунта не выдаются. Полный каталог статусов — `errors.json`.

Аналитика использует точные определения ADR-0016: 7/30/90 календарных дней, включая текущий день до исключённого начала следующего, в выбранном поясе. Отчёт сообщает границы, покрытие, ревизию, свежесть; дробные JSON-числа для тоннажа не нужны — `volume_g_reps` делится на 1000 только для вывода кг × повторения. Страницы серии сохраняют фильтры/границу в курсоре; итоговую сводку не рассчитывай по одной странице. Не объединяй оборудование/весовые соглашения или чужие данные.

Точка серии появляется только при наличии рабочих результатов данного упражнения; максимум без подходов не выдумывается. `complete` описывает покрытие серверного набора, а `next_cursor` — оставшиеся страницы: клиент не помечает график полностью загруженным до сохранения всех страниц. В полной сводке пропущенный день активности означает ноль; в неполной — отсутствие подтверждённых данных, не ноль.

Телеметрия ограничена отдельной схемой событий, без произвольного текста/URL/учётных данных Monium. `accepted`/`dropped` — диагностический ответ, не квитанция тренировочной очереди. Её доставка не блокирует тренировку и не использует надёжный outbox. Политика согласия/пределы Monium уточняются в P11; схема не разрешает включить неутверждённый сбор данных.

| API-02 | Старт → подход → завершение, потеря ответа/одновременный повтор | Одна запись/ревизия/квитанция в реальной транзакции YDB |
| API-03 | Конфликт двух устройств, зависимый суффикс и выбор пользователя | Нет затирания или потери ожидающих подходов/завершения |
| API-04 | Дельта H, новая запись во время страниц, просроченный bootstrap | Нет пропусков и продвижения курсора до локального commit |
| API-05 | Старый schema 1/план после долгой паузы, неизвестная новая версия | Повтор не исполняется заново по TTL, неизвестный формат не стирает очередь |
| API-06 | Черновик/проверка без одобрения, изменение base/digest/редакции | Нет публикации до нужного одобрения; проверка не даёт лишнего права |
| API-07 | Кнопка Gym, потеря ответа, повтор через MCP, отзыв grant | Одна версия программы, правильный клиент/владелец и запрет отозванного доступа |
| API-08 | Исправление истории и новая явная программа | Статистика пересчитана, прошлые снимки прежние, автоматических прибавок нет |
| API-09 | Реальный MCP SDK/целевой аккаунт: discovery, регистрация, PKCE/resource/scopes | Проверены transport/version/метаданные и чтение/запись; manifest не подменяет эту проверку |
| API-10 | Периоды/пояс, неполный кэш, разные тренажёры, пагинация серии | Нет ложного покрытия/свежести или смешения несопоставимых серий |
| API-11 | Лимиты тела/глубины, ошибки зависимостей, отказ YDB/неопределённый commit | Нет частичного исполнения и фиктивного подтверждения |
| API-12 | PWA на iPhone/Android, выход/обновление во время запроса | `/api`, `/auth`, `/oauth`, `/.well-known`, `/mcp` не кэшируются как оболочка; локальные данные сохранены |

Сейчас автоматически проверяются DTO/локальные инварианты/артефакты и согласованность примеров, а не все свойства таблицы. SDK, роли, Catalog/YDB, реальный OAuth-клиент, Gateway и мобильные устройства — последующая реализация/приёмка P03.2/P06–P10. Не заменяй её моками или зелёным тестом схемы.
