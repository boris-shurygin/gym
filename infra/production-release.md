# Production: продвижение и восстановление (P05)

Стейбл выпускается вручную через `Production release` в GitHub Actions. Укажи точный `release_id` и операцию `prepare` / `promote` / `rollback`. Workflow доступен только с main, использует защищённый Environment production/OIDC и очередь `gym-production-release` без отмены выполняющегося run. Merge не запускает production. Подготовка P05 сама по себе не разрешает фактический выпуск.

## Допуск и порядок

До изменения окружения проверяются репозиторий/владелец, SHA, workflow, конкретные run/attempt staging и успех всех gate/build/publish/migrations/deploy. Из приватного staging-бакета читается каноническая квитанция того же выпуска, затем по её SHA-256 — канонический manifest и все готовые файлы. Operator-validation и неполный/неуспешный staging отклоняются. Старый успешно проверенный выпуск допустим; новый production workflow исполняется из актуального main, а пакеты продвигаются без пересборки.

Обычный выпуск проверяет фактический Gateway и активный worker, записывает неизменяемое намерение с прежним release ID, выполняет ограниченные миграции в YC и устанавливает те же API/PWA-байты с production-конфигурацией. Gateway переключается после подготовки API и статики. После HTTPS smoke появляются квитанция установленного выпуска и отдельный результат операции. Секретов в публичной конфигурации нет; исходные пакеты обоих окружений одинаковы.

Поддерживаются короткие схемы `0001_runtime_metadata` и `0003_workouts_sync` с совместимостью Gym v1. Первый additive-переход 0001 → 0003 выполняется отдельной операцией `prepare` того же защищённого workflow: только миграции, без переключения приложения. Перед последующим `promote` оператор настраивает точечные runtime-права и отдельный OAuth по [регламенту](production-runtime.md). Неизвестные переходы, downgrade и rollback к другой ревизии запрещены. Первоначальный bootstrap служебных таблиц остаётся отдельной операторской задачей в облаке; CI не включает bootstrap/recovery и не получает прямых DML/DDL-прав YDB.

Editor включает удаление целевых API/Gateway/контейнера; код удаления не выполняет. ActAs разрешает запуск кода с правами целевых SA, включая DDL мигратора. Бакеты и backend остаются приватными, публичен только HTTPS Gateway. API не получает прикладного allowlist и DDL. Production CI не получает прямых YDB-прав; staging CI и издатель не получают доступа к production. Обновления общих политик добавляют только чтение production CI и сохраняют прежние ограничения.

После применения прав и отдельного согласия на первоначальный выпуск: `python -m infra.production_bootstrap --yc .local/bin/yc.exe --release <проверенный-release-id>`. Это проверяет staging-кандидата, создаёт служебную схему через metadata SA в приватном контейнере и возвращает обычный worker. Затем выпуск запускается через GitHub с обязательным одобрением Environment, а не прямыми командами локального компьютера.

## Повтор и восстановление

Каждая операция сохраняет `deployments/operations/<run_id>_<attempt>/intent.json` с прежним выпуском/хешем Gateway; результат появляется там же как `result.json` только после smoke. GitHub artifact содержит план и успешный результат, Summary — URL/выпуск. При сбое сначала установи фактическое состояние, не доверяй одному коду завершения HTTP.

- Ошибка допуска/хеша останавливает все изменения приложения/worker.
- После потерянного ответа миграции читай durable status того же job. `needs_resume` продолжается тем же выпуском; `running`/`repair_required`/неизвестное состояние останавливают автоматизацию. Новый выпуск не вытесняет незавершённый старый job.
- Повтори `promote` того же release ID через новый dispatch или Re-run production: совпадающие worker, API-тег и файлы переиспользуются. Намерение/результат отдельного run неизменяемы, постоянные ключи не создаются.
- Для отката выбери прежний release ID из намерения и `rollback`. Проверяются прежний успешный staging, наличие успешной квитанции установки в этом окружении и точная совместимость с активной схемой. Меняются только API/PWA/Gateway; активный worker и БД остаются текущими. Повтор отката также допустим.
- Неизвестная конфигурация, конфликт lease, другой checksum или несовместимая схема требуют отдельного разбора. Полный recovery с подтверждением остановки старого worker описан в [регламенте миграций](migration-worker.md); его нельзя включить простым параметром обычного workflow.

Readiness/status повторяются ограниченно только после сетевого/5xx-сбоя; шаги/создание ревизий и изменение Gateway вслепую не повторяются. Диагностика содержит HTTP-код и тип ошибки, без credentials/сырых ответов. Для staging частичный Re-run может сохранить outputs прежнего attempt: используй согласованный новый выпуск после полного push CI, как записано в [журнале](../docs/development-log.md), пока отдельный протокол повторов staging не реализован.

IAM-привязка бакета возвращает асинхронную операцию: дождись её завершения ограниченными чтениями через [канонический Operation.Get](https://yandex.cloud/en/docs/storage/api-ref/Operation/get), не повторяй PATCH из-за одного `done: false`. Перед продолжением после сбоя перечитай фактический план. Если назначение уже появилось, повтор выдачи не нужен.

## Проверка готовности

До PR выполняются тесты допуска/изоляции окружений, неизменяемой публикации, порядка операций, частичной миграции/потери ответа, повтора и совместимого отката. Реальная репетиция на staging использует тот же оркестратор и два уже опубликованных успешных выпуска с восстановлением исходного приложения. Проверки production, выдача прав, bootstrap и первый запуск выполняются только после конкретного согласия; их факты и ограничения записываются в журнал. Не объявляй P05 завершённым до подтверждения его приёмочных сценариев.

Проверка 2026-10-29: 179 локальных Python-тестов успешны (включая 91 release). На настоящем staging проверены promote/повтор для выпуска `9a16a2f…_40852028322_1`, rollback/повтор к `f0b99d6…_40765558574_1`, затем восстановлен исходный выпуск. Повторы не меняли control plane; rollback изменил только спецификацию Gateway, активный worker/схема сохранились. Неизменяемые delivery-байты в репетиции кэшировались в памяти после чтения, а состояние окружения и HTTP smoke каждый раз проверялись заново. Production оставался пустым; отдельная проверка подтвердила известную bootstrap-спецификацию с добавленным YC точным `servers`-origin.
