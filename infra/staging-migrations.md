# Оркестрация миграций staging (P04.3.2.1)

Этот подпункт добавляет в `Staging release` защищённый job миграций после `publish`. Приложение/Gateway остаются прежними; их выкатка — P04.3.2.2. Production не используется.

## Конкретный план доступа

Операторский `python -m infra.staging_access --yc .local/bin/yc.exe` только читает состояние. `--apply` добавляет следующие привязки после проверки владельца, приватности и отсутствия лишних прав:

| Субъект | Ресурс | Доступ |
| --- | --- | --- |
| staging CI `aje1ia9cf3t1g7o5p6pg` | контейнер `bba0n53on27kvvqler17` | `serverless-containers.editor`: развёртывание ревизии и приватный вызов |
| тот же CI | SA мигратора `ajedn74q9psjfecqnteg` | `iam.serviceAccounts.user`: назначение SA ревизии |
| тот же CI | delivery-бакет `e3e9b3p987mraociqtio` | `storage.viewer` плюс Allow GetObject только blobs/releases в bucket policy |

`editor` включает удаление данного контейнера. `iam.serviceAccounts.user` позволяет запустить код с уже существующими DDL-правами мигратора; проверенный main остаётся границей доверия (ADR-0013). Скрипты не удаляют контейнер и не меняют DDL-права. CI не получает прямого доступа к YDB, прав на API/Gateway/PWA, production или другие SA. Издатель сохраняет прежние ограничения условной записи. Неизвестная политика/лишние привязки останавливают применение; IAM из CI не меняется.

2026-10-28 пользователь явно разрешил эти постоянные привязки и первичный bootstrap. Права применены; повторный план не содержит изменений. Production и другие SA не затрагивались.

## Порядок выполнения

Job требует успешной публикации того же run, Environment `staging` и OIDC с точными repository ID/main/workflow/SHA/run/attempt и subject staging. Манифест читается из фиксированного delivery, сравнивается с digest, полученным от publisher; проверяются канонизация/схема, release/source/run/attempt и хеши/размеры всех файлов до изменения контейнера.

Контейнер получает только образ по digest из манифеста, фиксированный staging endpoint/namespace `gym_`, metadata SA и release ID. GitHub runner не подключается к YDB и не выполняет SQL. Ресурсы ограничены 512 MiB/1 core/120 секунд, concurrency 1, min instances 0, лимит 1 экземпляр/запрос на зону. Автоматический recovery, произвольные SQL/endpoint/SA и передача ключей в контейнер отсутствуют.

Первоначальные служебные таблицы создаёт оператор **в контейнере** отдельным bootstrap-режимом, затем возвращает обычный worker. `--bootstrap` подготавливает только административные таблицы и обычный режим; additive-миграцию затем инициирует CI. CI bootstrap не выполняет. Оркестратор читает health/status, вызывает ограниченные шаги и считает успехом только `succeeded` с ожидаемыми release/checksum/revision. После потери ответа сначала читается status; неизвестное/running/repair_required состояние останавливает процесс и требует разбора. Существующий lease не вытесняется по TTL.

При повторе того же выпуска используется тот же job ID, при совпадении конфигурации не создаётся новая ревизия. Для успешного задания проверяется реальная схема внутри worker. Неудачный шаг не разрешает продвижение к API/PWA. Результат CI сохраняется отдельным GitHub artifact; публикация артефактов сама по себе не означает успешные миграции.

Проверки до merge: локальные тесты отказов/идемпотентности, реальная оркестрация оператором и коротким токеном staging CI на опубликованном main-выпуске. Bootstrap, два шага и повтор успешны; в staging 5 таблиц, поколение задания 2. Запись в delivery, выпуск IAM мигратора, production и анонимный вызов worker отклонены с 403. YDB разрешает служебную сессию, но чтение `gym_runtime_metadata` возвращает `AccessDenied` (ответ запроса ABORTED); это не доступ к данным/DDL. Сессия пробы закрыта. Новый staging OIDC в этом workflow проверяется после отдельного merge.

Отдельно доказаны права deploy/actAs: staging CI создал одну идентичную ревизию с тем же image digest, SA и лимитами. Активна `bbao40rh7vapji9hugcj`; затем штатный оркестратор дважды вернул тот же результат generation 2 без новой ревизии. Основной код не создаёт дубликат при совпадении конфигурации; принудительное создание было только одноразовой capability-пробой.

## Операторская проверка

Для известного опубликованного выпуска передай точные release ID и digest манифеста. Первый bootstrap выполни отдельно, затем проверь CI и повтор:

```powershell
& ./.local/backend-venv/Scripts/python.exe -m infra.staging_migrations --yc .local/bin/yc.exe --release <release_id> --manifest-sha256 <sha256> --bootstrap
& ./.local/backend-venv/Scripts/python.exe -m infra.staging_migrations --yc .local/bin/yc.exe --release <release_id> --manifest-sha256 <sha256> --as-staging-ci
```

Локальная проверка использует короткие IAM через авторизованного оператора, без постоянных ключей. В CI этот же модуль самостоятельно получает staging OIDC после проверки GitHub run; аргументы оператора там недоступны. Результат сохраняется в `.local/staging-migrations.json` (CI) или `.local/staging-migrations-operator.json`; не считай его smoke приложения.
