# P11: диагностика, копии и приёмка staging

Объём — staging, облако `b1ghmudqihbvpnscd2fq`, каталог `b1ghdeobqrevsim6jg9o`.
Production не меняется. Согласование продуктовых параметров и контакта владельца ещё ожидается.

## Предлагаемые параметры

- Диагностика PWA выключена по умолчанию; согласие отдельно для аккаунта и устройства, отзыв очищает буфер.
- Отдельный ограниченный буфер: максимум 100 событий, TTL 24 часа, пакет до 20/16 KiB,
  попытка раз в минуту только в активном окне; после четырёх неуспешных попыток события отбрасываются.
- Сервер: две посылки в минуту на аккаунт, фиксированные имена/коды, без личных данных.
  Экспорт OTLP JSON в Monium Logs синхронно, тайм-аут 0,7 с без повторов;
  сбой возвращает accepted=0/dropped=N и не влияет на тренировки.
- Очищенные сводки HTTP: шаблон маршрута, серверный trace_id, статус/код, длительность и release_id.
  Без query/headers/тел/исключений, пользовательских ID и значений тренировок.
  Monium Logs: TTL 31 день. Полные трассировки и отдельный коллектор не нужны.
- Штатные метрики Gateway/Functions/YDB и эксплуатационные уведомления — минимум пилота.
  Внешняя проверка `Staging health` каждые 15 минут вызывает только публичный readiness
  (проверяет соединение с YDB без чтения личных строк), максимум три попытки.
  GitHub не получает облачных прав. Доставка оповещений владельцу согласуется отдельно.
- YDB уже имеет ежедневное расписание в 17:00 UTC с TTL 604800 с, deletion protection,
  лимитом 10 RU/с и 1 GiB; повторное расписание не создаётся.
  Цели RPO ≤24 ч и RTO ≤4 ч проверяются отдельно от наличия расписания.

## Точные новые права

Для Monium нужен API-ключ, отдельный от GitHub OIDC; это требование текущего OTLP endpoint.
Ключ только `yc.monium.logs.write`, срок 90 дней, хранение в отдельном Lockbox staging.
Значение не должно попадать в файл, Git, JS-сборку, stdout или CI.

| Субъект | Ресурс | Назначение |
| --- | --- | --- |
| новый SA `gym-staging-telemetry` | только каталог staging `b1ghdeobqrevsim6jg9o` | `monium.logs.writer`, только запись журналов |
| существующий SA API `ajeffa6opd0qko82m4de` | только новый отдельный секрет Monium staging | `lockbox.payloadViewer`, подключение конкретной версии к API |

Новых прав YDB, доступа GitHub к данным/ключу, production-ролей и публичных ресурсов нет.
У CI уже есть editor/actAs для API: доверенный main-workflow способен выпускать код от имени
SA API и косвенно использовать его разрешения. Прямое чтение Lockbox из workflow не добавляется;
значение ключа не проходит через исполнитель GitHub.
Создание обоих новых ресурсов также требует согласия: фиксированные имена `gym-staging-telemetry`
и `gym-staging-monium` только в указанном staging-каталоге. После создания сохрани полученные ID
в несекретной конфигурации. Lockbox создаётся с защитой удаления; значение ключа передавай
напрямую из памяти процесса в stdin Lockbox, без промежуточного файла и вывода.
Автоматическая проверка отклонила первоначальную попытку создания: отдельного согласия
на новые SA/Lockbox ещё нет. До согласия ресурсы и права не создавай.

## Проверка восстановления

Первый реальный запрос YC отклонён с `InvalidArgument: Have running backups for database`.
Статус исходной базы RUNNING, целевой изолированный путь не появился. Задания резервирования
не отменялись. До разрешения конфликта готовность восстановления не подтверждена.

Безопасный вариант обхода: создать временную **отдельную** serverless YDB
`gym-p11-restore-20261031` только в staging-каталоге, с лимитами 10 RU/с, 1 GiB,
нулевой резервированной мощностью и меткой `gym-purpose=p11-restore`. Восстановить готовую
копию туда штатным YC API, проверить схему/чтение и отказ доступа SA основного API, затем
удалить только эту доказанно временную базу. Новые роли CI/приложения не требуются;
исходные базы, копии, расписание, лимиты и production остаются прежними. Этот вариант
требует согласия на создание и удаление временной YDB до применения.

Проверенные команды (ID временной базы подставляется только после сверки имени/метки/каталога):

```powershell
yc ydb database create --name gym-p11-restore-20261031 --folder-id b1ghdeobqrevsim6jg9o --serverless --sls-throttling-rcu 10 --sls-enable-throttling-rcu --sls-provisioned-rcu 0 --sls-storage-size 1GiB --labels gym-purpose=p11-restore
yc ydb database restore <temporary-database-id> --backup-id <ready-staging-backup-id> --async
```

Следующее описание — проверка в изолированном пути существующей базы, если нет конфликта
с текущими заданиями backup; это не разрешение повторять запрос при неизвестном исходе.

Выбери готовую штатную копию именно YDB `etn63tldguvkj5kcpi3r`. Восстанови её штатным YC API
в новый изолированный путь `gym_p11_restore_<UTC-время>` внутри staging. Исходные таблицы
не перезаписывай, API продолжает использовать только корневые `gym_*`.
Проверь наличие схемы, чтение восстановленных таблиц и отсутствие runtime-доступа к копии;
строки/сессии/тренировки не выводи и не выгружай в GitHub. Зафиксируй backup ID, operation ID,
счётчики, длительность и результат в `.local/`. Удаляй только доказанно созданную область
этой проверки, после успешной проверки; не удаляй штатные копии или исходные таблицы.
