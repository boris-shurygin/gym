# Ротация тегов API

[ADR-0018](../docs/adr/0018-function-tag-retention.md): текущая и две предыдущие различные успешные установки, одинаково для staging и production. Общий [deploy](staging_app.py) вызывает [TagRetention](function_tags.py) после проверки миграций, до создания версии, и после smoke/неизменяемой квитанции. Production promotion и rollback используют этот же deploy. Операторский синтетический режим `v-*` исключён.

## Границы

| Окружение | Единственная функция | Единственный Gateway |
| --- | --- | --- |
| staging | `d4efel2j20be6tq27cr1` | `d5d734k3s76t42pa5rtn` |
| production | `d4ee3u6hgmh6hf4ccrpn` | `d5dhqvda3eo6r4c2mgf6` |

Используй существующий `serverless-functions.editor` CI только своей функции. Читай приватные квитанции своего PWA-бакета и архивы delivery существующим доступом. Новых IAM/ACL нет. Мутации: `Function.Update` с **updateMask=labels** и сохранением остальных labels, `Function.RemoveTag` только доказанно принадлежащих Gym тегов `r-[0-9a-f]{32}`. Не меняй `$latest`, посторонние теги, IAM, YDB, версии функции, архивы или Gateway в рамках очистки.

Перед снятием тега проверь полные списки версий, соответствие окружения/SA/API ZIP, квитанцию при её наличии, канонический манифест и наличие/хеши всех его артефактов. Архив неудачного кандидата проверяется тоже. План защищает фактическую цель Gateway, три успешные установки и входящий кандидат. Неполный список, неизвестная история, отсутствие архива или нехватка места из-за посторонних тегов останавливают очистку.

История атомарно записывается в четыре метки функции. Если ответ PATCH потерян, считай результат по контрольному чтению. Сбой после квитанции до меток восстанавливается по фактическому Gateway и его успешной квитанции. Сбой до квитанции оставляет старое успешное окно и дополнительно защищает фактический Gateway. Параллельное ручное изменение окружения запрещено; перечитывай Gateway/метки/привязку перед каждым снятием тега. Не обещай общей транзакции нескольких ресурсов.

## Однократный переход

До включения ротации staging успешно устанавливал P06 `15a2ad…_40909363405_1`, P07 `b138d10…_40949467086_1`, затем P08 `54aee729…_41048520945_2`. Production установлен на `9a16a2f…_40852028322_1`. Полные ID зафиксированы в `LEGACY` кода. Инициализируй историю только при совпадении текущего Gateway и подтверждении всех квитанций/тегов. Не определяй предшественника сортировкой даты создания функции. При расхождении сначала выясни фактическую историю.

Первый staging-план оставляет P08/P07/P06 и снимает семь более старых тегов. Production-план сохраняет единственный текущий тег и ничего не снимает. Снятие одноимённого старого staging-тега production-релиза не затрагивает отдельную production-функцию.

Операторский просмотр без изменений:

```powershell
& ./.local/backend-venv/Scripts/python.exe -m infra.function_tags --environment staging --yc .local/bin/yc.exe
& ./.local/backend-venv/Scripts/python.exe -m infra.function_tags --environment production --yc .local/bin/yc.exe
```

`--apply` выполняет только обслуживание тегов **текущего** выпуска в выбранном окружении, без выпуска приложения. Применяй в отсутствие работающего deploy, в пределах согласованной пользователем политики. Обычные следующие релизы выполняют обслуживание автоматически; production workflow запускай только при разрешённом выпуске.

Квитанции неизменяемы и содержат прежний function-version ID. Если тег уже снят, не воссоздавай его под старой квитанцией. Для восстановления вне окна опубликуй новый проверенный выпуск; совместимость схемы и обычные gate обязательны. Сохранение двух тегов не разрешает downgrade YDB.

Источники: [Function.Update](https://yandex.cloud/en/docs/functions/functions/api-ref/Function/update), [RemoveTag](https://yandex.cloud/en/docs/functions/functions/api-ref/Function/removeTag), [срок жизни версий](https://yandex.cloud/ru/docs/functions/concepts/function).
