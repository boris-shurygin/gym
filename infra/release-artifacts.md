# Манифест и публикация артефактов

P04.1 реализует формат выпуска и условную публикацию байтов в delivery. Автоматическая выкатка ещё не включена: образ/исполнитель миграций и роли относятся к P04.2, доверенная сборка и staging workflow — к P04.3. Слияние P03 подтверждено через PR #9 и успешный CI main.

## Состав выпуска

`release.schema.json` задаёт закрытый формат v1: полный main SHA, ID/attempt запуска сборки, runtime `python312`, entrypoint `index.handler`, digest образа миграций в принятом Registry, целевую ревизию схемы, совместимость API/очереди и список файлов с SHA-256/размером/HTTP-метаданными.

`release_id` строится как `<main_sha>_<run_id>_<attempt>`. Повтор сборки того же SHA — отдельный кандидат, а продвижение версии использует прежние байты и хеш манифеста. Набор должен содержать API ZIP, шаблон Gateway и полную PWA. Физический каталог подготовки:

```text
release-input/
  api.zip
  gateway.json
  web/
    index.html
    service-worker.js
    manifest.webmanifest
    assets/...
```

Храни манифест отдельно от этого каталога. Обязательные файлы, хеши/размеры и фактический список должны совпадать. Неожиданные файлы, ссылки, обход путей, совпадения без учёта регистра, закрытые служебные маршруты и неподдержанные типы ресурсов отклоняются. Для API проверяются entrypoint, отсутствие корневого установочного requirements.txt, безопасность путей ZIP, размер/CRC и поддержанное сжатие. Для PWA требуется относительный корень того же origin; ресурсы `web/assets/` получают длительный immutable cache, точки входа — `no-cache`.

Текущие пределы инструмента: 128 MiB на объект, 256 MiB на набор файлов, до 2000 артефактов и до 1 MiB канонического JSON манифеста. Это ограничения первой реализации. Миграционный образ не подменяется ZIP: требуется URI с digest, а его реальная сборка/проверка выполняется в P04.2. До неё настоящий полный выпуск ещё не сформирован.

## Команды

Используй окружение Python с `api/requirements.txt`. После подготовки реальных файлов и опубликованного образа миграций:

```powershell
& ./.local/backend-venv/Scripts/python.exe -m infra.release_artifacts create --root .local/release-input --output .local/release-manifest.json --main-sha $releaseMainSha --run-id $releaseRunId --attempt 1 --migration-image $migrationImageDigest --revision 0001_runtime_metadata
& ./.local/backend-venv/Scripts/python.exe -m infra.release_artifacts publish --root .local/release-input --manifest .local/release-manifest.json
```

Передай временный IAM-токен в окружение процесса `GYM_IAM_TOKEN`, не в аргумент командной строки или Git. Команда публикации адресована только настроенному delivery-бакету; роли CI пока не расширены. На Linux используй соответствующий Python из venv.

## Порядок публикации

Сначала полностью проверь манифест и все локальные байты. Затем отправь каждый уникальный объект под `blobs/sha256/<digest>`. Последним условным PUT отправь канонический манифест под `releases/<release_id>/manifest.json`; его SHA-256 вычисляется по этим же байтам. Сбой загрузки ресурса не создаёт манифест неполного выпуска. Уже загруженные, но не связанные с манифестом blobs остаются до отдельной политики очистки; автоматически удалять их при сбое нельзя из-за общих ссылок/параллельных публикаций.

Каждый PUT содержит `If-None-Match: *` и Content-MD5. При занятом ключе выполняется GET и сравниваются **фактические** SHA-256/размер, а не только пользовательские метаданные объекта. Совпадение допускает идемпотентный повтор; иное содержимое останавливает публикацию. Потеря ответа PUT также разрешается чтением объекта; если записи ещё нет, повтор выполняет только условный PUT, максимум три попытки. Безусловного перезаписывающего PUT нет.

HTTP-клиент использует IAM Bearer напрямую, без постоянных S3-ключей и дополнительной подписи. Redirect не переносит токен на другой адрес. Ошибки содержат код/тип проблемы, без токена или тела ответа провайдера. Это поведение инструмента; IAM и политика доступа бакета настраиваются отдельно в P04.2.

Поля `build` описывают происхождение, но структурно допустимый JSON **не доказывает** доверенный main или успешный staging. Код выкатки должен проверить реальный workflow, run/attempt/SHA и результаты нужного выпуска через доверенный CI; production дополнительно требует согласованного gate. Эти проверки входят в P04.3/P05. Одна публикация манифеста не даёт права развёртывания.

## Проверки

```powershell
& ./.local/backend-venv/Scripts/python.exe -m unittest discover -s tests/release -p 'test_*.py' -v
```

16 тестов проверяют предвалидацию, подмену/пропуски файлов, порядок публикации, относительные пути, ZIP/CRC, ошибочные метаданные и поведение S3-клиента при конфликте/потере ответа/redirect. Они не обращаются к облаку и включены в job `api`.

На настоящем Object Storage отдельно проверены одинаковый повтор, отклонение другого содержимого и два параллельных автора одного ключа: создаётся один объект, второй автор получает конфликт. После проверки оба собственных объекта из случайного префикса `checks/p04-1/` удалены. Временный IAM-токен оставался в памяти; результат без секретов сохранён локально. Реальная PWA-сборка и ранее проверенный API ZIP также проходят инвентаризацию/проверку формата без создания вымышленного выпуска.
