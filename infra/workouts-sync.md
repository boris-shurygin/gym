# Сервер занятий и квитанций — P07

Пользователь разрешил весь P07 автономно: реализация, PR, CI, merge и проверенный staging. P08, MCP и production не входят. Решения протокола — [ADR-0015](../docs/adr/0015-workout-snapshots-and-sync.md), точные DTO — [контракты](../contracts/README.md); готовность реального выпуска сверяй с [журналом](../docs/development-log.md).

## Прикладные операции

[Workouts](../api/workouts.py) реализует list_plans/get_plan, list_workouts/get_workout, submit_operation/get_receipt, bootstrap/get_changes. HTTP использует существующие bindings и тот же прикладной слой. Личность и active-допуск повторно проверяются внутри каждой транзакции; для записи через PWA обязательны Origin/CSRF. IAM, device_id и expected_owner_id не заменяют сессию.

Сервер выдаёт конкретные fixed-v1 цели всех шаблонов опубликованной программы. План сохраняет собственный ID, время расчёта и history_revision. Публикация/изменение истории инвалидирует текущий набор; list_plans/bootstrap синхронно готовят свежий fixed-v1 набор. Прежние планы остаются доступны для отложенного старта на срок жизни аккаунта. Клиент не присылает серверу свои цели.

В SERIALIZABLE-транзакции фиксируются занятие, неизменяемая ревизия, аудит с исходной операцией/заявленным временем, событие изменения, инвалидирование показателей и квитанция. На повтор сначала проверяй прежнюю квитанцию и digest всей операции, затем предусловие. Неопределённый commit разрешается исходным ID; технический повтор допускается только после подтверждённого abort. [Гарантии транзакций YDB](https://ydb.tech/docs/en/concepts/transactions) проверяются отдельной native suite в CI.

Окончательный отказ корректной операции тоже коммитит неизменяемую rejected-квитанцию и исходное намерение в аудите. HTTP возвращает её в ErrorResponse.error.receipt. Неизвестная зависимость даёт dependency_pending без окончательной квитанции; сохраняются хеш и ссылка для обнаружения циклов. Подмена тела под тем же ID запрещена и для ожидающей операции. Предшественник обязан относиться к тому же владельцу/занятию; его успешная ревизия не подменяется последней ревизией занятия.

Рабочие подходы занимают первую свободную цель, затем идут дополнительные с последней целью сравнения; разминка не занимает слот. Исправление не меняет цель при прежнем типе. При смене рабочего/разминочного типа сервер проверяет новую связь. Удаление оставляет tombstone; дополнительные подходы не продвигаются в освободившиеся позиции. Завершённое занятие можно исправить, сохранив снимок и время завершения; отменённое терминально. Два устройства могут начать разные активные занятия.

## Хранение и согласованная выдача

Миграция [0003_workouts_sync](../db/migrations/versions/0003_workouts_sync.py) добавляет только gym_workout_records с PK `(owner, key)` и JSON payload. Прежние аккаунты, сессии и программы не переписываются. Физическое представление — развитие документного Store P06; столбцы владельца входят во все запросы. Runtime не создаёт таблицы.

| Ключ записи | Назначение |
| --- | --- |
| plan:, plans | Неизменяемые выданные планы и текущий набор |
| workout:, revision: | Текущая проекция и неизменяемые ревизии занятия |
| operation:, pending: | Квитанции/digest и ещё не разрешённые зависимости |
| audit:, rejection: | Принятые правки и окончательно отклонённые намерения |
| meta, event: | Последовательность владельца, history_revision и ссылки на неизменяемые данные |
| history:, active:, completed: | Небольшие индексы ссылок для истории/bootstrap |
| manifest:, cursor: | Зафиксированные наборы/границы страниц и серверные курсоры |
| operation_window | Ограничение новых операций одного владельца |

Публикация программы атомарно добавляет program_published в ту же последовательность. Выдача нового набора создаёт plans_changed; запись занятия — workout_changed и stats_invalidated. Событие хранит ссылку на конкретную ревизию, а не на изменяемую текущую строку.

Bootstrap включает текущую программу/планы, все активные и последние 30 завершённых занятий. Манифест ссылок формируется одной согласованной транзакцией, живёт 15 минут; страницы читают именно эти версии. История тоже фиксирует набор ссылок; её курсор связан с владельцем, фильтром и размером страницы. Дельта замораживает H при первом чтении курсора, повтор страницы сохраняет результат; новые события после H доступны в следующем цикле. Курсор дельты действует 30 дней, квитанции от этого не истекают. Чужой/истёкший курсор требует bootstrap и не даёт чужих данных.

## Технические границы и проверка

- Формат/байты запросов и максимумы объектов остаются контрактными. Дополнительные эксплуатационные пределы первой реализации: 240 новых operation_id в минуту на владельца, до 256 неразрешённых звеньев при поиске цикла; прежняя квитанция доступна и при rate limit.
- Проекция занятия и манифест ссылок ограничены 512 KiB каждый. Страницы содержат до 100 объектов и до 900 KiB полезных данных; сервер вправе вернуть меньше запрошенного limit. Слишком большой согласованный набор возвращает явную ошибку, не частичный bootstrap. Масштабирование манифестов больших аккаунтов требует отдельного продолжения; лимит не удаляет историю/очередь.
- Истёкшие манифесты/курсоры и события старше окна логически недоступны для продолжения. Физическая уборка временных метаданных ещё не автоматизирована; неизменяемые версии, аудит, планы и минимальные квитанции сохраняются. Это эксплуатационное ограничение, не разрешение удалять квитанции по TTL.
- Локальные тесты [общих сценариев](../tests/api/test_workouts.py) выполняются также на [настоящей одноразовой YDB](../tests/ydb/test_workouts.py), где дополнительно проверяются конкурентные повторы, конфликт и независимые старты. [Миграционный тест](../tests/ydb/test_integration.py) проверяет 0002→0003 с сохранением прежних данных.
- Приёмка staging использует два временных синтетических аккаунта через настоящий HTTPS API и затем удаляет только их fixtures. Настоящий аккаунт владельца не заполняется тестовыми тренировками.

PWA пока сохраняет занятия локально и не вызывает эти новые маршруты. Перенос очереди, отправка/повторы и экран выбора при конфликте относятся к P08. Аналитические расчёты, кроме признаков инвалидирования, — P09/P10; MCP — P10.2. Успешный health сам по себе не подтверждает новый ACL или выполнение прикладных операций.
