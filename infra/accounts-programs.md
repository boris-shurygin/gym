# Аккаунты и версии программ — P06

Этап выполняется автономно по запросу «Сделай P06 полностью»: код, проверки, PR, CI, merge и staging. Production этим запросом не разрешён. Выбор Яндекс ID, закрытого допуска и серверного одобрения остаётся в [ADR-0014](../docs/adr/0014-user-sessions-and-agent-authorization.md).

## Хранение и инварианты

Внешний callback Яндекса принимает служебные дополнительные query-параметры провайдера, затем передаёт общему сервису только `state`, `code` либо `error`. Это соответствует [RFC 6749 §4.1.2](https://www.rfc-editor.org/rfc/rfc6749#section-4.1.2); Яндекс также [документирует error_description](https://yandex.ru/dev/id/doc/ru/codes/code-url). Внутренний CallbackInput и остальные прикладные DTO остаются закрытыми. Неоднозначные/повторные параметры, отсутствие state/binder, истечение и повтор callback отклоняются. Сообщения об отказах различают устаревший вход и отказ провайдера, не раскрывая параметры или описания ошибок провайдера.

Additive-миграция `0002_accounts_programs` создаёт пять таблиц. Каждая содержит составной PK `(owner, key)` и проверенный JSON `payload`; это выбор представления P06, а не новая модель продукта. Чтения/изменения идут через SQLAlchemy/YDB в SERIALIZABLE, без DDL из HTTP. Повтор транзакции разрешён только после подтверждённого abort; обмен кода Яндекса выполняется вне повторяемой транзакции после необратимого claim.

| Таблица | Назначение | Права staging API |
| --- | --- | --- |
| `gym_admissions` | Уникальный hash проверенного subject → внутренний user_id и active/disabled | describe/select |
| `gym_login_transactions` | State, hash binder, PKCE verifier до claim, срок и общий лимит начала входа | describe/select/update/erase |
| `gym_sessions` | Hash непрозрачной cookie, владелец, subject hash и сроки | describe/select/update/erase |
| `gym_login_requests` | Только подтверждённые Яндексом заявки, hash subject и reference | describe/select/update/erase |
| `gym_program_records` | Профиль, черновики, проверки, неизменяемые версии/публикации и квитанции request_id, разделённые user_id | describe/select/update/erase |

Runtime не может выдать допуск самому себе. У каждой прикладной операции заново проверяются сессия/допуск и expected_owner_id, объект ищется в разделе подтверждённого владельца. Чужой change_id возвращает not_found. Имя/email/YC-организация не создают личность Gym. Вход не назначает первого пользователя администратором.

Публикация проверяет показанные редакцию, digest всей Proposal и базовую версию, recent auth <10 минут и статус validated. Одобрение кнопкой и создание версии атомарны; request_id и отдельная квитанция публикации возвращают прежний результат после потери ответа. В P06 отдельная передача неиспользованного одобрения MCP не реализована: publish_approved может только прочитать уже состоявшуюся публикацию с точным approval_id. Делегирование grant/scopes — P10.2. Автоматическая прогрессия не добавлена: конкретные цели остаются fixed-v1.

## Точный план доступа staging

Для Alembic добавлена служебная `gym_schema_version`: постоянный PK `name='schema'`, номер ревизии — отдельный столбец. Это необходимо, поскольку YDB запрещает UPDATE первичного ключа прежней `gym_alembic_version`. Под migration lock проверенная legacy-0001 копируется в новый формат; старый указатель не меняется/не удаляется. Неизвестная legacy-ревизия запрещает переход. Таблица остаётся административной, API не получает к ней доступа.

Цель — только YDB `etn63tldguvkj5kcpi3r` в каталоге `b1ghdeobqrevsim6jg9o`, SA API `ajeffa6opd0qko82m4de`. Применение [ydb-access.json](ydb-access.json) выдаёт только права таблицы выше. Корневого DML, DDL/GRANT, доступа к административным таблицам, production или прямого доступа CI не добавляется. Сначала миграция доверенного main, затем операторский plan/apply и отрицательные пробы. Повтор должен давать пустой план.

OAuth использует отдельный секрет Lockbox `e6qd458h1rc6me3s7htp` в этом же staging-каталоге: один ключ `client_secret`, фиксированная активная версия `e6qu9dcqjlhb4hc5u6js`. Пользователь зарегистрировал Client ID `7cba5f50f12c44788311ba106f1bca8a` и внёс секрет скрытым локальным вводом. Операция `e6qpv3fkvkdc9dl70ntr` завершена успешно; payload агентом не читался. Только staging API `ajeffa6opd0qko82m4de` получает `lockbox.payloadViewer` **на этот конкретный секрет**. GitHub не получает его payload, роль payloadViewer или токен Яндекса. Несекретные ссылки записываются в [staging-auth.json](staging-auth.json). Production не наследует staging OAuth.

Проверь план командой `python -m infra.accounts_access`; `--apply` применяет только таблицу выше и указанную роль на этот секрет. Инструмент проверяет Client ID, каталог, версию/ключи секрета, целевой SA и существование таблиц до первой мутации. Он запрещён в CI. После применения повтор плана должен быть пустым. PR #19 доставляет миграцию с выключенным входом; включение OAuth выполняется следующим PR после проверки ACL. Полный P06 принимается после проверки реального входа на новом Gateway-выпуске.

## Подключение Яндекс ID

1. Зарегистрируй «Gym staging» типа «Для авторизации пользователей» в [Яндекс OAuth](https://oauth.yandex.ru/). В «Доступ к данным» выбери «Логин, имя и фамилия, пол» (`login:info`); почта (`login:email`) для Gym не нужна. Callback: `https://d5d734k3s76t42pa5rtn.764nr5vy.apigw.yandexcloud.net/auth/callback/yandex`. После сохранения проверь поле `scope` публичной карточки `https://oauth.yandex.ru/client/<client_id>/info`: оно должно содержать только `login:info`. Если Яндекс возвращает `invalid_scope`, сопоставь это поле с запрашиваемым scope; исправь настройки приложения, а не расширяй запрос Gym. Затем начни свежий вход. [Правила scope](https://yandex.ru/dev/id/doc/ru/codes/code-url), [настройка доступа к данным](https://yandex.ru/dev/id/doc/ru/register-auth).
2. Client ID не секрет. Client secret не присылай в чат/PR и не записывай в Git. Внеси его локально через [Set-GymStagingOAuth.ps1](../scripts/Set-GymStagingOAuth.ps1): скрытый ввод передаёт значение в YC API в памяти через проверенное HTTPS, не через аргументы процесса/файл. Скрипт печатает только ID ресурса/версии.
3. После проверки минимальной роли секрет подключается к новой версии Cloud Function через штатную интеграцию Lockbox. Точные параметры, cookie, callback и scopes проверь на реальном HTTPS Gateway. [Документация передачи секретов](https://yandex.cloud/ru/docs/lockbox/operations/serverless/functions), [PKCE](https://yandex.ru/dev/id/doc/ru/codes/code-url), [получение личности](https://yandex.ru/dev/id/doc/ru/user-information).
4. При первом подтверждённом входе неприглашённый получает not_invited с безопасным trace_id/reference. Оператор сверяет, какому приглашённому человеку принадлежит reference, и разрешает **именно эту** заявку. Нельзя одобрять последнюю/первую неизвестную заявку автоматически.

```powershell
& ./.local/backend-venv/Scripts/python.exe -m infra.accounts_admin --yc ./.local/bin/yc.exe pending
& ./.local/backend-venv/Scripts/python.exe -m infra.accounts_admin --yc ./.local/bin/yc.exe allow --reference <reference>
```

После допуска повтори обычный вход. `disable --reference <reference>` блокирует все сессии этого пользователя на следующих запросах; повтор allow сохраняет user_id. Допуск друзей выполняется тем же операторским способом. Production-процедуру этот CLI намеренно не принимает.

## Клиент и ограничения

На staging установлен выпуск `2f5b696…_40884012127_1` с включённым OAuth; [CI выпуска](https://github.com/boris-shurygin/gym/actions/runs/40884012127) и независимая проверка артефактов/API/Gateway/схемы успешны. Пользователь отдельно разрешил точный план прав; apply выполнен, повтор пуст, запреты записи допуска и чтения служебных данных проверены от имени API. Payload секрета агентом не читался.

Через настоящий HTTPS и Chrome проверены два временных аккаунта: серверная изоляция, Origin/CSRF, повтор публикации и отказ устаревшей базы; кнопка PWA опубликовала вторую версию, сохранив снимок начатого занятия. Проверены offline-перезагрузка с подходом и отзыв сессии/очистка cookie при выходе. Все собственные fixture-строки удалены. Вход настоящего владельца требует отдельной проверки провайдера и допуска по указанному им reference; синтетические проверки не назначают владельца автоматически.

Первый экран предлагает вход и отдельное демо. local-demo не импортируется. Сессия и CSRF хранятся только в cookie/памяти; IndexedDB получает только подтверждённый owner и программу. Планы кэшируются отдельно по владельцу, старые снимки занятий сохраняются. При истечении входа доступна локальная запись прежнего профиля, но серверная доставка ещё не реализована (P07/P08). Другой аккаунт требует явно открыть отдельный профиль. Выход/скрытие не удаляют историю/очередь; скрытие распространяется на вкладки и не обещает серверного отзыва.

Черновик открывается по `/#/program?change_id=<uuid>`. Перед одобрением видны текущий и предложенный план с весами/повторениями и основание; ссылка повторного входа сохраняет ссылку черновика только в разделе его владельца. Полноценный редактор шаблонов и MCP не объявлены реализованными: подготовка/замена/проверка доступны через принятый REST-контракт.

Service worker исключает `/auth/`, `/oauth/`, `/.well-known/`, `/mcp` и `/api/` из navigation fallback и кэша. Уже установленный старый shell должен получить обновление перед использованием входа. Offline-профиль не зашифрован; данные доступны владельцу профиля браузера.

Истёкшие сессии/state отклоняются серверными часами независимо от удаления строк. Автоматическое удаление старых квитанций/проверенных заявок и распределённая защита от злоупотреблений сверх общего лимита входов ещё не настроены; размер YDB ограничен 1 GiB. До публичного доступа нужны согласованные сроки хранения и мониторинг. Нельзя удалять квитанции опубликованных версий произвольно или выдавать отсутствие автоочистки за TTL.

Production остаётся на прежнем выпуске/схеме 0001. Его gate отклоняет 0002 до отдельного точного плана перехода, новых ACL/OAuth-конфигурации и явного разрешения выпуска. Это не блокирует автономную приёмку P06 на staging.
