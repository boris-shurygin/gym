Синтетические таблицы удалены; независимая проверка показывает 0 таблиц. Контейнер возвращён в обычный режим без fault/ticket. Автоматическая выкатка приложения — P04.3.

Проверенный образ — `cr.yandex/crpe91o8ka9e03n3n90c/gym-migrations@sha256:869d3e4fbe1c6d9c188c1039685e3c3d4afdb6075c6cf4f56cf5cd6f87179fe8`; активная staging-ревизия `bbamv40o2q1qstiijrbh`, release marker `validation_1be6b55c22f8180579563968a0e705267ece8914`. Образ построен и проверен в [ручном CI](https://github.com/boris-shurygin/gym/actions/runs/40528247737), затем проверен оператором в облаке. Это validation-only, не промышленный выпуск. Обычный namespace `gym_` ещё не инициализирован: health подтверждает процесс, не готовность схемы приложения.

## Образ и границы доступа

[Dockerfile](migrations.Dockerfile) закрепляет Python 3.12/Linux amd64 по digest и устанавливает готовые зависимости из [db/requirements.txt](../db/requirements.txt). Контекст [ограничен списком](../.dockerignore), процесс работает под UID 10001. В образ входят только API-подключение, строгий JSON-парсер, миграции и worker; авторизация оператора, `.local/`, web и Git не копируются. `MetadataUrlCredentials` требует закреплённый `requests` с зависимостями: одного YDB SDK недостаточно.

`scripts/build_worker_image.py` собирает образ и проверяет настоящий HTTP health в режиме metadata с недоступной тестовой БД: старт/health не должны обращаться к YDB или получать токен. Затем сохраняет Docker archive, его SHA-256, source SHA, ревизию и checksum миграций. Ручной job `migration-image-validation` в Cloud access выполняется только для `workflow_dispatch` рабочей ветки: нет Environment, OIDC, облачных секретов или публикации. Артефакт живёт 7 дней и имеет назначение `validation-only`; это не доверенный выпуск main и не кандидат для production. Основная сборка/манифест/допуск появятся в P04.3/P05.

Оператор может перенести проверенный архив в реестр штатным `regctl image import` без Docker на Windows; проверь digest ZIP из GitHub, SHA-256 архива, исходный SHA и config digest после импорта. Запускай контейнер только по полученному manifest digest, не по тегу. В текущем окружении локальный credential helper передаёт IAM-токен regctl через память процессов; ключей и токенов в конфигурации нет. Такой импорт — отдельная ручная проверка staging, не обход защиты GitHub Environment для промышленного выпуска.

## Staging и конфигурация

[migration_container.py](migration_container.py) работает только с контейнером `bba0n53on27kvvqler17` в staging и реестром `crpe91o8ka9e03n3n90c`. Без `--apply` показывает план. Проверяет принадлежность ресурса, запрет публичных bindings, фиксированную БД/metadata auth, образ по digest и существующие права. Мигратор получает только `container-registry.images.puller` на этот реестр в дополнение к [правам staging YDB](ydb-access.md). CI не получает новых ролей; токены оператора не передаются в контейнер.

Ревизия использует 1 core/512 MiB, concurrency 1, timeout 120 секунд, 0 подготовленных экземпляров, максимум 1 экземпляр и 1 запрос на зону. Это до трёх зон, не обещание одного процесса на всё облако: единственность работы обеспечивает YDB lease. Metadata GCE включена, AWS IMDSv1 выключена, облачное логирование пока выключено. Код печатает только случайный request ID, status/state/code; сырые исключения/SQL/параметры/токены не возвращаются. Настройка журналов и мониторинга позднее не должна расширять доступ CI к данным.

Режимы выбираются **конфигурацией ревизии**, не телом запроса:

| Режим | Разрешённое действие |
| --- | --- |
| `bootstrap` | Создать/проверить только служебные lock/jobs/migration_requests внутри облака |
| `worker` | Выполнить один шаг известной миграции или прочитать статус |
| `recovery` | Восстановить строго одно задание по ticket из конфигурации; шаг миграции недоступен |

БД, prefix, release ID и mode задаёт оператор/доверенный deploy-код. HTTP принимает только `operation`, `release_id`, `checksum` и для step/status — `job_id`. Запрос не задаёт SQL, БД, путь, номер checkpoint, владельца или recovery ticket. Тело ограничено 16 KiB, запрещены дубли ключей, неизвестные поля и некорректное обрамление. Внешний доступ к URL административного контейнера проверяет IAM платформы; не публикуй контейнер через Gym API/Gateway и не выдавай `allUsers`/`allAuthenticatedUsers` права вызова. Локальный HTTP-сервер используется только как тестовый стенд.

```powershell
# Только план; подставь настоящий digest опубликованного образа.
& ./.local/backend-venv/Scripts/python.exe -m infra.migration_container --image 'cr.yandex/crpe91o8ka9e03n3n90c/gym-migrations@sha256:<digest>' --release '<release_id>' --mode bootstrap
# --apply создаёт ревизию; затем административным IAM POST вызови bootstrap.
# Переключи ту же пару image/release в mode worker перед обычными шагами.
```

Повтор совпадающей конфигурации не создаёт ревизию. При потере ответа deploy проверь реальную активную ревизию/операцию перед повтором; ошибка клиента не означает отсутствия результата. Конфигурация и digest проверяются повторным чтением после deploy. CLI намеренно запрещён в GitHub Actions; отдельный доверенный инструмент main создаётся в P04.3. Production здесь не поддерживается.

## Шаги, состояния и повтор

Служебная `migration_requests` связывает неизменные job/release/checksum с поколением, владельцем, checkpoint и recovery receipt. Первоначальная пустая staging-схема проверена отдельно; существующая несовместимая служебная таблица останавливает bootstrap, не меняется автоматически.

`migration_jobs` хранит внутреннюю квитанцию Alembic-expand. Полный статус worker берётся из `migration_requests` через HTTP, не из этой внутренней квитанции: успех expand ещё требует отдельной проверки завершающего шага.

1. В одной serializable-транзакции проверь job/release/checksum, захвати общую блокировку, запиши новое поколение/владельца и `running`. Конкурирующий запрос получает `migration_busy`; таймер не вытесняет владельца.
2. Первый шаг выполняет известную короткую additive-ревизию `0001_runtime_metadata`, проверяет фактическую схему и сохраняет checkpoint 1 / `needs_resume`. Это не универсальный backfill: новые длинные/многошаговые миграции требуют собственных ограниченных операций/checkpoint.
3. Следующий вызов ещё раз проверяет фактическую схему/ревизию, затем сохраняет checkpoint 2 / `succeeded`. Запись результата и освобождение lease выполняются вместе после проверки владельца. Старый владелец не может записать состояние после смены lease.
4. Повтор завершённого job и чтение `succeeded` проверяют реальную схему; cached success не скрывает удалённую/изменённую таблицу. Иной release/checksum для того же job отклоняется.

Бюджет шага — 60 секунд до начала следующей SQL-операции; RPC ограничены 5 секундами, ожидание сессии — 5 секундами, скрытые повторы SDK отключены. Это не доказательство отката при таймауте: холодный старт/RPC/неясный commit могут закончить вызов ошибкой. Предел платформы 120 секунд — дополнительная защита, не разрешение автоматически снять lease. Ничего не продолжает миграцию после HTTP-ответа. При неясном исходе сначала читай статус того же job; `running`/`repair_required` и удержанный lease требуют восстановления. Несколько DDL не являются общей транзакцией; автоматического downgrade нет.

## Административное восстановление

Обычный `worker` не принимает recovery-параметры и не умеет снимать чужую блокировку. Требуется отдельная доверенная recovery-ревизия того же контейнера; право публиковать код/конфигурацию остаётся административной границей доверия (ADR-0013), а не защитой от злонамеренного владельца этого права.

1. Останови обычную выкатку и прочитай известный job: release/checksum, owner и generation. При неизвестном job или другом артефакте не продолжай автоматически.
2. Подтверди остановку старого исполнителя. Для текущего синхронного worker переведи старую ревизию в `OBSOLETE`, проверь его timeout 120 секунд и отсутствие фоновых DDL, затем выжди **180 секунд от подтверждённого переключения**. Это ручная процедура прекращения старой работы, не TTL lease. Для иных worker/долгих YDB operations такого ожидания недостаточно: нужны отдельное подтверждение завершения/operation ID и проверка фактической схемы.
3. Сохрани несекретное свидетельство: `old_revision`, целочисленное UTC-время `observed_obsolete_at`, `execution_timeout_seconds: 120`, `quiescence_seconds: 180`, `job_id`, `owner`, `generation`. Ticket содержит точные `job_id`, `owner`, `generation`, `not_before` и `evidence_sha256` — SHA-256 от `json.dumps(evidence, sort_keys=True).encode()`. `not_before` не должен быть раньше конца ожидания. CLI требует оба файла (`--ticket` и `--evidence`): проверяет соответствие данных/hash/интервала и заново читает список ревизий staging-контейнера — прежняя должна быть `OBSOLETE`, того же digest и SA, в HTTP-режиме с timeout 120 секунд. Сам worker **не получает прав читать control plane и не доказывает внешнюю остановку**. Ticket — утверждение доверенного оператора, его hash — запись об использованном свидетельстве, не криптографическое доказательство остановки.
4. Опубликуй recovery-ревизию с `GYM_RECOVERY_TICKET`, затем ещё раз проверь старую ревизию/ожидание. Вызови `recover` с release/checksum. Ранний вызов отклоняется. В одной транзакции сравниваются job, release, checksum, generation и **текущий** owner lease; только точное совпадение сохраняет recovery receipt, `needs_resume` и удаляет блокировку. Иное поколение/владелец не меняются. Повтор того же recovery до нового шага возвращает прежний receipt.
5. Верни обычную worker-ревизию без ticket и возобнови тот же job. Следующее поколение перепроверяет фактический результат/схему. Не меняй содержимое прежнего job, не делай автоматический downgrade и не пересоздавай таблицы ради отметки успеха.

Включение recovery-режима требует оператора/deploy-права; один JSON-флаг в обычном запросе ничего не разрешает. В production отдельный gate, свидетельство остановки и процесс восстановления проверяются в P05; этот staging-инструмент не объявляет их готовыми.

Синтетический crash доступен только через конфигурацию ревизии с префиксом `gym_worker_probe_<случайный_id>_` в конкретной staging YDB. HTTP не включает его. Проверка должна закончиться возвратом обычного worker без fault/recovery-конфигурации и удалением только собственных тестовых таблиц. Не используй этот режим на прикладном namespace.
