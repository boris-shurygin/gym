# Доверенная сборка и публикация (P04.3.1)

`Staging release` в [deploy-staging.yml](../.github/workflows/deploy-staging.yml) запускается после **Web checks / push main**, а не после PR. В этом подпункте он только публикует выпуск; миграции, развёртывание API/PWA/Gateway и smoke будут в P04.3.2. Шаблон Gateway пока содержит заглушку 503. Production не запускается.

## Происхождение и права

1. `gate` без облачных прав читает GitHub API: неизменяемые ID репозитория/владельца, workflow Web checks, событие push, успешные обязательные jobs, SHA/попытку запуска. Исходники workflow и актуальный main должны совпадать с проверенным SHA. Если main уже продвинулся, запуск останавливается; дождись CI нового main.
2. `build` без OIDC собирает готовый ZIP API на Python 3.12/Linux с native smoke, PWA, шаблон Gateway и Linux-образ миграций с metadata health. Зависимости фиксированы; пересборки в publisher нет. Bundle содержит полные хеши/размеры, исходный SHA и назначение `release`.
3. `publish` скачивает bundle только своего run, независимо повторяет допуск через GitHub API и проверяет все байты. После этого получает GitHub OIDC и обменивает его на короткий IAM издателя `aje0omi931fri66pbdir`. Claims ограничены точными repository ID, main ref, workflow, source SHA, run/attempt; подпись проверяет YC. IAM не сохраняется на диск и не выводится.
4. Docker загружает проверенный архив, сверяет config digest, публикует образ в `gym-migrations` с уникальным тегом `release-<release_id>`. Выпуск использует **digest**, а не тег. API/PWA/Gateway публикуются [условным PUT](release-artifacts.md); манифест записывается последним. Ошибка загрузки образа/файла не создаёт готовый манифест.

`release_id = <40-символьный-main-sha>_<run_id>_<attempt>`. Повтор всего workflow получает новый attempt; файлы с одинаковыми хешами переиспользуются. Полного одинакового digest образа при пересборке не обещаем. При частичном сбое могут остаться неиспользованные blob/образ; автоматической очистки пока нет.

Публикация видна в GitHub Actions → **Staging release** → `publish` → Summary; там указаны `releases/<release_id>/manifest.json` и digest образа. Зелёный результат P04.3.1 означает публикацию пакетов, а не выкатку приложения. Первое выполнение этого нового workflow возможно только после его merge в main.

## Первоначальные права издателя

Локальный оператор сначала получает план:

```powershell
& ./.local/backend-venv/Scripts/python.exe -m infra.delivery_access --yc .local/bin/yc.exe
# Применяй после проверки конкретного плана:
& ./.local/backend-venv/Scripts/python.exe -m infra.delivery_access --yc .local/bin/yc.exe --apply
```

Сценарий фиксирует delivery-бакет и один репозиторий, проверяет закрытость, отсутствие bucket ACL и лишних прямых/унаследованных прав издателя. Неизвестная политика останавливает применение; чужие правила не перезаписываются. Настройка прав не запускается из CI.

Политика delivery разрешает издателю чтение `blobs/sha256/*` и `releases/*`, запись только туда с `If-None-Match: *`. Перезапись без условия/с другим условием, удаление и изменение политики/ACL явно запрещены. Права существующего оператора сохранены. Постоянных S3-ключей нет. Эта политика ещё не предоставляет чтение будущим staging/production jobs: их доступ добавляется отдельно.

В YC bucket policy является дополнительным фильтром: перед ней требуется [базовый IAM/ACL-доступ](https://yandex.cloud/en/docs/storage/security/overview). Поэтому план включает `storage.uploader` **только на бакет** `e3e9b3p987mraociqtio`, без роли на каталог. Сначала сценарий устанавливает/повторно читает ограничивающую политику, затем добавляет IAM через [UpdateAccessBindings](https://yandex.cloud/en/docs/storage/api-ref/Bucket/updateAccessBindings), сохраняя чужие привязки. Одна политика без базового IAM дала 403 даже на чтение в реальной пробе. Политика, registry pusher и отдельная привязка `storage.uploader` применены 2026-10-28 после явного согласия пользователя; повторный план не содержит изменений.

Реальная проверка с коротким токеном издателя успешна: условное создание, повтор одинаковых байтов и конфликт разных; запись без условия, вне разрешённого префикса, удаление, изменение ACL и политики дают 403. Неподдерживаемое значение `If-None-Match` отклоняется провайдером с 501, байты остаются прежними. Чтение/запись того же manifest образа по прежнему digest успешны, теги не менялись. Метаданные каталогов staging/production и staging YDB недоступны издателю (403). Все собственные синтетические ключи удалены оператором. Эта проба использует impersonation оператора; новый publisher OIDC в GitHub проверяется отдельно после merge.

В Container Registry роль `container-registry.images.pusher` ограничивается репозиторием `crpbvi15g2kc6667ksdh`, **но включает удаление образов и репозитория**. Это ограничение [роли провайдера](https://yandex.cloud/en/docs/container-registry/security/), а не гарантия WORM: код издателя не удаляет образы, digest защищает от подмены содержимого, но не от исчезновения образа. Защищённый main и проверка workflow остаются границей доверия (ADR-0013). Прав на YDB и каталоги staging/production издатель не получает. Не проверяй delete на реальном образе выпуска.

## Проверка рабочей ветки до merge

В **Cloud access → Run workflow** выбери рабочую ветку и `validation_target=release-bundle`. Этот job без Environment/OIDC/облачных прав выполняет тесты выпуска, собирает тот же набор с назначением `validation-only` и сохраняет его на 7 дней. Издатель такой bundle отклонит. Для отдельного образа доступен `migration-image`.

Локальные тесты не требуют облака или Docker:

```powershell
& ./.local/backend-venv/Scripts/python.exe -m unittest discover -s tests/release -p 'test_*.py' -v
```

Облачные проверки прав выполняются оператором на синтетических байтах: условное создание/повтор, запрет перезаписи/удаления/другого префикса/администрирования, чтение и запись существующего manifest образа по тому же digest. Первую настоящую федеративную публикацию main проверь после merge; ручная сборка ветки её не заменяет.
