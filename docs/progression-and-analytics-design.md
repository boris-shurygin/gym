# Прогрессия через агента и минимальная аналитика — P02.4.1

Обновлено: 2026-10-26. **Пользователь выбрал управление прогрессией через агента.** Для MVP сервер использует явные цели `fixed`; автоматическая двойная прогрессия отложена. Проект P02.4.1 принят пользователем 2026-10-26 командой «да, завершаем этап»; решения записаны в принятом [ADR-0016](adr/0016-progression-and-analytics.md). Расчётчик/API/аналитика ещё не реализованы.

Основа — ADR-0003, ADR-0008, [вход и одобрение](authentication-design.md) и [контракт снимков/синхронизации](workout-sync-design.md). P02.4 разделён на этот проект и отдельный P02.4.2 со схемами REST/MCP, ошибками и сквозной приёмкой. Числа примеров синтетические, не общие настройки программы.

## 1. Кто меняет цели

Подтверждено пользователем 2026-10-26: «давай пока прогрессией рулить через агента». Агент читает принятую сервером историю и показатели, обсуждает с владельцем новые нагрузки и предлагает редакцию программы. Пользователь одобряет конкретное изменение; сервер проверяет его и публикует новую неизменяемую версию. Следующие планы строятся из её явных целей.

Первый тип — `fixed`: для каждой плановой позиции программа задаёт вес и конкретное рекомендуемое число повторений. Разные подходы могут иметь разные цели. Ручная корректировка агентом — новая одобренная редакция этих данных, а не скрытый алгоритм увеличения нагрузки.

Сервер остаётся источником опубликованной программы, конкретных целей и показателей по ADR-0003. В начальном варианте его расчёт целей — детерминированное построение снимка из явных назначений. Это выбор первого правила в рамках принятой архитектуры; автоматические правила можно добавить отдельным решением позже.

Завершение занятия, превышение повторений/веса, тоннаж, пауза в занятиях и истечение времени сами не меняют цели. Нет автоматической прибавки/снижения веса, разгрузки или пересчёта тренировочной стратегии. Текущие цели сохраняются до следующей одобренной публикации. Неподдержанный тип правила отклоняется с ошибкой, а не переключается молча на `fixed`.

## 2. Путь изменения через агента

1. Получить свою текущую программу, принятую историю и показатели с ревизией/датой обновления. Локальные неотправленные результаты недоступны агенту через сервер; не считай такую сводку полной историей устройства.
2. Подготовить черновик изменения с базовой версией программы, новыми целями и обоснованием. Агент может предложить вес, повторения и число плановых позиций; фактическое число подходов прошедшей тренировки от этого не меняется.
3. Проверить структуру, владельца, допустимые значения и конкуренцию версий. Показать владельцу прежние/новые назначения и основание. Если статистика помечена устаревшей или появились новые принятые результаты, явно показать это при рассмотрении; не выдавать старые данные за свежие.
4. Владелец в Gym нажимает «Одобрить и опубликовать» для точной редакции по ADR-0014. Черновик, текст согласия в чате и OAuth-согласие сами не публикуют программу. Изменённый текст/база требуют нового одобрения.
5. Общий прикладной сервис атомарно публикует версию и расходует одобрение; повтор возвращает прежний результат без второй версии. Агент может прочитать итог. REST/MCP используют одни проверки, точные схемы/канонизацию закрепит P02.4.2.

Первоначальные права агента не включают исправление тренировочных фактов. Он предлагает программу, а записанные подходы корректирует пользователь через приложение. Показатели и готовая программа принадлежат конкретному пользователю; лендинг не делает их публичными.

## 3. Цели, числовая политика и выполнение

Для `fixed` обязательны ID каждой плановой позиции, `weight_g` и `suggested_reps`. Веса 0–2 000 000 г, повторения — целые 1–1 000 по ADR-0015. Кг переводятся в целые граммы точно, без скрытого округления. Если показан диапазон повторений, нужны явное рекомендуемое число и условие `min <= suggested_reps <= max`; диапазон не запускает автоматическую прогрессию.

Шаг кнопок веса задаётся упражнением и не заменяет явное назначение. Ни факт, ни цель не округляются к нему автоматически; пределы/точность проверяются сервером. Каталог сложных лестниц оборудования и определение эквивалентности разных тренажёров не добавляются этим решением. Объём считается в целых `weight_g × reps`; отображение кг может убрать незначащие нули, сохраняя точное значение.

Новый рабочий подход получает цель своей позиции; дополнительный — последней плановой позиции, с явной отметкой по ADR-0008/0015. План и факт разделены: можно выполнить меньше/больше, с другим весом/повторениями. Это сохраняется как факт и не переписывает программу. Разминка/дополнительные не заполняют чужие плановые позиции, удаление/смена типа сохраняет аудит.

Для пользователя/агента сервер может показать сравнение по исходным полям, не назначая автоматическую награду или штраф:

| Факты занятия | Следующие цели при той же опубликованной версии |
| --- | --- |
| Все плановые подходы по цели | Не меняются |
| Больше повторений или выше вес | Не меняются; факты доступны агенту для решения |
| Меньше/смешанные веса, неполная тренировка | Не меняются; нет автоматического снижения |
| Разминка и дополнительные подходы | Сохраняются отдельно; плановое число позиций не меняется |
| Несколько офлайн-занятий по одному снимку | Принимаются как отдельные факты без автоматических прибавок |

Пример одной программы: цели 60 кг × 10 и 65 кг × 8. Результаты 60 × 12 / 65 × 10 сохраняются; следующий план остаётся 60 × 10 / 65 × 8. Агент может предложить новые цели, но до их одобрения/публикации они не становятся планом. Машиночитаемые синтетические примеры — [progression-cases.json](examples/progression-cases.json); это ожидаемые результаты будущей реализации, не выполненные тесты сервера.

Процент объёма отдельного подхода по ADR-0008 — только сравнение: нет процента при нулевом знаменателе, равный тоннаж не означает одинаковый результат. Ни процент, ни сумма тоннажа не меняют цели автоматически. Отдельный индикатор числа рабочих подходов не заменяет сравнение исходных веса/повторений.

## 4. Версии, офлайн-работа и исправления

План хранит `program_version_id`, шаблон/позиции, ID/версию `fixed`, версию построения плана и ревизию истории, на которой он был выдан. Переименование, новое оборудование и изменение назначений публикуются через версионируемую программу; сопоставимость статистики задаётся отдельно. Серверного автомата ступеней/`basis_state_id` для `fixed` не требуется.

Начатое занятие закрепляет исходный серверный снимок. Новая одобренная программа меняет только будущие свежие планы. Старый подлинный план принимается после новой публикации по ADR-0015 с видимой версией/предупреждением; сервер не переинтерпретирует старые факты как выполнение новых целей. Устройства без сети не выдумывают новые назначения.

После исправления/удаления истории сервер пересчитывает показатели и повышает их ревизию. Кэш/основание выданных планов помечаются устаревшими по ADR-0015; свежий план при той же программе содержит те же явные цели, с обновлёнными метаданными. Исправление факта само не создаёт новую программу и не отменяет ранее одобренные назначения. Агент может учесть исправленную историю в следующем предложении.

Пример: пользователь исправил старый подход с 60 × 10 на 60 × 8. Аудит и статистика изменились, исходный снимок занятия остался прежним. Следующая цель не стала 57,5 или 62,5 кг автоматически. Если уже была опубликована новая программа, она остаётся текущей до отдельного одобренного изменения.

Возврат производных данных содержит `history_revision`, версию расчёта и статус `fresh`/`stale`/`recalculating`. Расчёт для H не публикуется как свежий для H+1: перед фиксацией проверяется ревизия основания. Повтор задания даёт те же показатели без дублирования фактов. Пока пересчёт не готов, прежние показатели/планы можно показать с отметкой устаревания; локальная запись не должна ждать расчёта.

## 5. Минимальные показатели

Начальный набор — история и три вида представления: активность по датам, вес с фактическими повторениями, объём рабочих подходов. Формулы используют только текущие принятые сервером результаты завершённых занятий.

| Показатель | Определение | Ограничения |
| --- | --- | --- |
| Тренировки по дням | Число завершённых занятий с хотя бы одним неудалённым рабочим подходом | Пустое/только разминочное занятие остаётся в истории, но не увеличивает этот показатель |
| Рабочие подходы и повторения | Число неудалённых рабочих результатов и сумма их повторений | Включая дополнительные; не смешивать с плановым числом подходов |
| Объём упражнения за занятие | `sum(weight_g × reps) / 1000`, единица кг × повторения | Включая дополнительные рабочие; разминка исключена из этого показателя |
| Наибольший рабочий вес за занятие | Максимум фактического веса; рядом повторения соответствующего подхода | При равном весе выбрать наибольшие повторения; исходные подходы доступны в истории |
| План и факт | Исходные цели/результаты и соотношение объёма отдельного подхода по ADR-0008 | Нет процента при нулевом знаменателе; это не критерий прогрессии |

Активные/локально ожидающие занятия видны в журнале отдельно, но не включаются незаметно в серверный отчёт. Удалённые результаты не входят в актуальные суммы, оставаясь в аудите. Нулевой внешний вес сохраняется; из него не выводится масса тела.

Сопоставимая серия имеет ключ `(exercise_id, equipment_id, weight_convention)`. Другое оборудование/соглашение/логическое упражнение — отдельная серия; одинаковое название не объединяет данные. Внутри такой серии можно показывать факты разных шаблонов с указанием источника; плановые цели по-прежнему относятся к своим позициям шаблонов. Не суммируй тоннаж несопоставимых упражнений в показатель роста силы. Оценка 1ПМ, «эффективного веса», тренировочного эффекта и автоматические выводы о здоровье не входят в начальный набор.

### Периоды, время и кэш

Начальные периоды — 7/30/90 календарных дней. Границы задаются в сохранённом часовом поясе аналитики пользователя, начало включается, конец исключается; после смены пояса нужен новый запрос. Пояс нужно выбирать при первом входе с подсказкой браузера, до выбора явно использовать UTC. Переходы времени не подменяются прибавлением одинакового числа миллисекунд к каждому дню.

Дата занятия берётся из сохранённого заявленного времени начала, отдельно от времени приёма сервером. Подозрительное время помечается, а не молча заменяется датой синхронизации. Конкретные схемы времени/диапазонов/ошибок — P02.4.2.

Ключ кэша включает владельца, период/границы, часовой пояс, сопоставимую серию, версию аналитики и ревизию истории. Сохраняй полученные серверные сводки за начальные периоды и последние открытые графики; в интерфейсе показывай время обновления и полноту покрытия. При открытии/возврате сети/ручном обновлении запрашивай актуальные данные; фоновое выполнение не требуется.

Без сети можно показать сохранённый серверный отчёт с отметкой устаревания. Локальные 30 занятий из P02.3 не равны полной истории за 90 дней: не выдавай вычисленную по ним неполную сумму за серверную сводку всего периода. Если отчёт не был загружен, показывай отсутствие данных; локальные факты доступны в журнале. Кэш аналитики восстановим и может очищаться раньше очереди/активных/недоставленных данных. Личная статистика лендинга использует те же определения и авторизованный API.

## 6. Будущие приёмочные сценарии

Это требования к P03.2/P06/P09/P10, не выполненные тесты расчётчика/API.

| ID | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| PROG-01 | Полное выполнение явных целей | Следующие назначения той же версии не меняются |
| PROG-02 | Выше вес/повторения/процент объёма | Факты сохранены, автоматической прибавки нет |
| PROG-03 | Агент создал/проверил черновик без одобрения | Текущая программа и планы прежние |
| PROG-04 | Одобрена/опубликована точная редакция | Новая версия для будущих планов; повтор не создаёт вторую |
| PROG-05 | Подменён текст/база, истёкшее/повторное одобрение | Публикация отклонена, нужны предусмотренные ADR-0014 проверки |
| PROG-06 | Старая офлайн-тренировка доставлена после публикации | Старый снимок и факты сохранены, новые цели в неё не подставлены |
| PROG-07 | Неполное занятие, разминка/дополнительные, смешанные веса | Нет скрытой правки программы или замены плановых позиций |
| PROG-08 | Исправлена/удалена история | Пересчитаны показатели, программа сама не меняется |
| PROG-09 | Нет сети/есть локальная очередь, агент читает сервер | Видна ревизия/полнота серверных данных, непринятые факты не выдуманы |
| PROG-10 | Десятичный вес, цель вне формата и иной шаг кнопок | Точное сохранение либо ошибка, без скрытого округления |
| PROG-11 | Чужие данные или попытка агента исправить факт без права | Серверный отказ независимо от переданного ID |
| PROG-12 | Во время расчёта H принята правка H+1, затем повтор задания | Устаревшая сводка не помечена свежей; результат идемпотентен |
| PROG-13 | Долгая пауза/повторное завершение/неподдержанный тип правила | Нет автоматической разгрузки/прибавки или скрытой подмены типа |
| STAT-01 | Завершённое, активное, отменённое, только разминочное занятия | Согласованные фильтры активности/рабочих сумм, история не потеряна |
| STAT-02 | Дополнительные/удалённые подходы и равный максимальный вес | Верные суммы и выбор пары вес/повторения |
| STAT-03 | Разное оборудование/весовое соглашение и чужой аккаунт | Серии не смешаны, чужие данные недоступны |
| STAT-04 | Нет сети, есть 30 занятий и нет полного отчёта за 90 дней | Нет ложной полной суммы/свежести |
| STAT-05 | Граница периода, смена пояса и поздняя синхронизация | Дата факта отделена от времени приёма; границы/кэш согласованы |

## Точка продолжения

Управление прогрессией через агента, без автоматической двойной прогрессии в MVP, подтверждено. Представления целей/показателей, кэш и будущая приёмка приняты вместе с проектом; рабочий сервер ещё не реализован. После проверки и слияния P02.4.1 следующий P02.4.2 закрепляет формальные схемы, канонизацию/digest, маршруты/ошибки и публикацию программы. Весь P02 пока не завершён.
