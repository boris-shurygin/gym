# ADR-0014: Вход пользователя, серверные сессии и делегирование агенту

- **Статус:** Принят пользователем 2026-10-26 командой «Завершаем этап» после проверки проекта P02.2
- **Дата:** 2026-10-25
- **Связано:** ADR-0001, ADR-0002, ADR-0004, ADR-0010, ADR-0013

## Контекст

Локальный клиент реализован без настоящего входа. Нужны отдельные личные аккаунты, сохранность очереди при повторной аутентификации и ограниченная запись через MCP. Настроенный GitHub OIDC подтверждает CI и не решает вход пользователей. Поставщик личности и политика допуска до P02.2 не были согласованы.

## Решение

1. Использовать Яндекс ID и ограничить допуск приглашёнными — владельцем и друзьями (оба выбора подтверждены пользователем 2026-10-26). Email, Telegram и MAX рассмотрены и в первый вариант не включены. Привязка: свой user_id Gym связывать с проверенным subject Яндекс ID, без получения пароля и автоматического объединения разных идентичностей по присланной строке email/логина.
2. Выполнять обмен code + PKCE на сервере. Для PWA/личной веб-статистики выдавать непрозрачную отзываемую сессию Gym в Secure/HttpOnly host-only cookie; проверять CSRF/Origin изменяющих запросов и права на каждый объект. Токены внешнего провайдера в браузер/агент не передавать.
3. Сохранить локальные разделы и очередь при истечении входа/выходе. Отправлять операции только после проверки личности прежнего владельца; тестовый local-demo автоматически в аккаунт не переносить. Подробные состояния/конфликты определить в P02.3.
4. Для MCP использовать OAuth-компонент Gym с ограниченными scopes/resource и серверным отзывом, поверх внешнего входа пользователя. Первый вариант — предварительная регистрация разрешённого клиента; возможности CIMD/DCR не объявлять реализованными. Использовать проверенную библиотеку OAuth, не собственную криптографию. Конкретная совместимость целевого ChatGPT проверяется на стенде до выпуска MCP.
5. Отделить согласие на OAuth от одобрения публикации: владелец в Gym подтверждает точную редакцию/базу/содержание изменения, а общий прикладной сервис проверяет и расходует это одобрение. Текст агента или поле approved не дают такого права.

Подробные потоки, начальные сроки, хранение секретов, источники и приёмка — в [authentication-design.md](../authentication-design.md). Ни один из этих потоков пока не реализован в приложении.

## Альтернативы и компромиссы

- Другой внешний поставщик — возможен по выбору пользователя; нужен свой подтверждённый поток, без предположения о совместимости с Яндекс ID.
- Собственные пароли/ссылки входа — добавляют хранение/восстановление или доставку почты; для первого варианта не нужны.
- Provider token в браузере/MCP — смешивает внешнюю личность и прикладные права; выбранная схема сохраняет их раздельно.
- Внешний полноценный OAuth/CIAM-сервис может упростить MCP, но требует отдельного выбора размещения/данных/стоимости. Компонент Gym сохраняет принятый российский Yandex Cloud; его безопасная реализация требует отдельной проверки библиотек/протокола.
- CIMD упрощает дальнейшую регистрацию клиентов, но добавляет проверку внешних метаданных. Предрегистрация ограниченного пилота уменьшает эту часть реализации; расширять её нужно осознанно, согласно текущей спецификации MCP.

## Последствия

Понадобятся таблицы личности/допуска/сессий/OAuth/одобрений и миграции вне пользовательских запросов; разделение данных/секретов окружений; реальные тесты cookie через Gateway и запрета чужих операций. Приняты начальные сроки сессии PWA 7 дней неактивности/30 дней максимум, MCP access token 10 минут и refresh 30/90 дней, одноразовое одобрение на 10 минут. Основной путь — «Одобрить и опубликовать» в Gym. Формальные контракты и совместимость реализации проверяются в P02.3/P02.4, P06 и P10.2.

Этот ADR дополняет, не заменяет принятые требования. Проект входа/сессий и границы делегирования приняты; рабочий вход и MCP пока не реализованы. Не подменяй архитектурное решение результатами интеграционных тестов. Контракт PWA и границы реализации по этапам приведены в разделе 8 проекта.
