# ADR-0013: Окружения, артефакты выпуска и отдельное задание миграций

- **Статус:** Принят пользователем 2026-10-25 при запросе первоначальной настройки после обсуждения схемы
- **Дата:** 2026-10-25
- **Связанные решения:** [ADR-0009](0009-russian-hosting.md), [ADR-0010](0010-ydb-serverless-cloud-functions.md), [ADR-0011](0011-github-actions-cicd.md)
- **Подробный проект:** [Схема развёртывания](../deployment-design.md)

## Контекст

Автоматический staging после merge, ручной production, YDB и Cloud Functions уже приняты. Для реализации не хватает конкретного размещения окружений, способа описания инфраструктуры, состава неизменяемого выпуска и сервиса разового выполнения миграций в облаке.

Пользователь указал организацию `organization-b-shurygin` и существующее облако `b1ghmudqihbvpnscd2fq`, затем запросил настройку и согласовал бюджет до 3 000 ₽/месяц. Доступ оператора и активная оплата проверены. Первоначальная настройка выделена в P01.1; собственный домен остаётся открытым вопросом до пилота.

## Предлагаемое решение

1. В существующем облаке создать отдельные каталоги `gym-staging` и `gym-production`, а для пакетов выпуска — `gym-delivery`. В окружениях раздельные YDB, функции API, шлюзы, бакеты PWA, учётные записи и секреты. Общие артефакты не содержат пользовательских данных.
2. Начать со служебного HTTPS-домена каждого API Gateway. Через него раздавать PWA из приватного Object Storage и маршрутизировать `/api/v1` в Cloud Functions. Клиент использует относительные пути API. Собственный домен можно добавить до реального пользовательского пилота без пересборки JS, но смена origin требует отдельного плана переноса локальных данных PWA.
3. Описывать инфраструктуру версионируемыми конфигурациями и шаблонами OpenAPI; первоначальную настройку выполнять через `yc`/API из авторизованной среды оператора. Первоначальные сценарии просмотра/применения входят в P01.1, сценарии выпуска — в P04/P05. Обычные релизы изменяют только пакеты/версии/маршрутизацию, а не IAM. Terraform пока не вводить.
4. Один раз на доверенном main собирать ZIP API с готовыми зависимостями, PWA и образ миграций. Фиксировать SHA, SHA-256 файлов и digest образа. Хранить пакеты в приватном Object Storage, образ — в Container Registry. Production продвигает тот же выпуск без повторной установки зависимостей и пересборки.
5. Миграции выполнять отдельным приватным Serverless Container с собственной учётной записью. CI административно вызывает ограниченные шаги задания и читает только очищенный статус; DDL и заполнение данных выполняются внутри Yandex Cloud. Это отдельный исполнитель, не HTTP-обработчик Gym и не код старта/вызова функции API. Административный вызов контейнера сам использует HTTPS — это явно часть предлагаемой детализации, а не фоновая работа после ответа пользовательского API.
6. Хранить прогресс и блокировку задания в YDB, проверять реальную схему после DDL, поддерживать повтор одного `job_id`. Успешный административный запрос ещё не означает завершённую миграцию. Не продолжать выпуск, пока обязательное изменение схемы не подтверждено.
7. Первоначально сохранять пакеты/ресурсы выпуска не менее 90 дней; установленный production-выпуск и его рабочий предшественник не удалять по возрасту. До согласования P02 не удалять версии API или формат очереди только потому, что прошло 90 дней. Это предложение по хранению, а не разрешение терять старые несинхронизированные тренировки.

## Рассмотренные альтернативы

| Вопрос | Предлагаемый вариант | Альтернатива и компромисс |
| --- | --- | --- |
| HTTPS PWA | Один API Gateway для PWA и API | Прямой статический хостинг с отдельным доменом уменьшает число запросов через шлюз, но добавляет домен/HTTPS и CORS; можно вернуться к нему при росте трафика |
| Управление инфраструктурой | `yc`/API + шаблоны в Git | Terraform лучше отслеживает связи и изменения большого числа ресурсов, но требует отдельного решения о хранении/блокировке state. Его S3 backend нельзя автоматически считать работающим с OIDC только потому, что это умеет провайдер |
| Миграционный исполнитель | Приватный Serverless Container | Выполнение на GitHub runner запрещено ADR-0011; выполнение в функции API запрещено. Разовая Compute Cloud ВМ даёт полноценный процесс, но требует управления диском, сетью, завершением и удалением |
| Запуск контейнера | Синхронные ограниченные шаги с checkpoint | Асинхронный вызов контейнера у провайдера сейчас Preview; очередь с триггером добавляет ещё один сервис и семантику повторной доставки. Ни один вариант не отменяет необходимость блокировки/идемпотентности |
| Production | Ручной выбор выпуска, защищённое окружение | Полностью автоматический production изменил бы ADR-0011; не входит в это предложение |

## Последствия и проверки

- Нет постоянного CI-сервера или постоянно подготовленного миграционного экземпляра; добавляются Container Registry и административный контейнер, оплачиваемые по правилам провайдера.
- Все файлы PWA проходят через API Gateway; это влияет на стоимость запросов и требует проверки заголовков кэширования и поведения service worker.
- Сценарии `yc` должны обнаруживать расхождение конфигурации и повторный запуск, а не слепо создавать дубли или заменять ресурсы. Первоначальные сценарии и тесты находятся в `infra/` и `tests/infra/`; управление версиями приложения добавляется в P04/P05.
- Размер ZIP, нативные зависимости, точный Python runtime, роли YDB без DDL для API и пределы шагов миграций проверяются на синтетическом стенде в P03/P04. До этих проверок проект не считается рабочим деплоем.
- Доступ привилегированного deployment-кода остаётся границей доверия: возможность опубликовать код под сервисным аккаунтом миграций нельзя считать защитой от злонамеренного кода в main. Нужны защищённые ветка, окружения и проверка изменённых workflow.
- Этот ADR дополняет открытые детали и не заменяет ADR-0009–0011. Параметры подключения и предел затрат согласованы перед созданием пустой инфраструктуры; готовность приложения и возможность выпуска проверяются отдельно.
