# ADR-0026: Публикация программы доверенным Python-агентом

- **Статус:** Принят пользователем 2026-11-02: «Да, публиковать через агента по моему запросу»
- **Дата:** 2026-11-02
- **Заменяет:** обязательность отдельного одобрения каждой программы в Gym из ADR-0014/ADR-0021 для явно доверенного Python-клиента

## Контекст

Пользователь редактирует программу через агента и считает повторное одобрение в
приложении лишним. Он согласовал разовое разрешение доверенному агенту публиковать
по явному запросу в чате. Сервер не получает переписку и не может доказать наличие
такого запроса: это делегирование права публикации, а не новое доказательство
пользовательского нажатия. Агент обязан соблюдать границы запроса.

## Решение

1. Добавь отдельный OAuth scope `program:publish_direct`, доступный только
   зарегистрированному `gym-python`. Клиент запрашивает его явной командой
   `login --allow-program-publish`. Без флага сохраняются прежние scopes.
   Существующие grants не расширяются ни при обновлении сервера, ни при refresh.
2. Пользователь один раз видит и разрешает новое право на серверной странице
   OAuth Gym; она требует свежего Яндекс-входа. В списке подключений право названо
   явно и отзывается обычным отзывом grant. Сроки, владельцы и привязка окружения
   не меняются. Сам агент не нажимает OAuth-согласие за пользователя.
3. MCP-инструмент `publish_program_changes` принимает request ID, владельца,
   ID/редакцию проверенного черновика, базовую версию и digest. Он доступен только
   с новым scope. Внутри той же транзакции повторно проверь действующий grant,
   `client_id=gym-python`, владельца, создание черновика этим grant, валидацию,
   редакцию, digest и актуальную базу. Cookie-сессия не даёт этого права.
4. Создай неизменяемую версию, текущий указатель, событие синхронизации и квитанцию
   атомарно. Повтор идентичного request ID возвращает прежний результат; изменённое
   тело не становится повтором. Отзыв и истечение проверяются также при повторе.
   Начатые и прошлые занятия сохраняют снимки.
5. Квитанция прямой публикации содержит явное основание `delegated_agent`, client,
   grant и scope. Не создавай фиктивное одобрение пользователя или `approval_id`.
   Сохрани прежнюю публикацию через кнопку Gym и `apply_program_changes` для
   подключений без нового права. Их контракты и факты одобрений остаются прежними.
6. Опиши MCP-only операцию отдельно от REST-привязок. Её DTO и tool schema
   генерируются из тех же общих контрактов. Новые scopes в списке подключений и
   квитанция делегированной публикации требуют opt-in представления 2; старый
   клиент получает `upgrade_required` до фиксации изменяющего запроса.

## Последствия и границы

Новый grant даёт агенту право публиковать собственные проверенные черновики без
отдельного клика для каждой редакции. Ошибка агента может изменить будущую
программу; сохранённые версии и отзыв позволяют восстановить контроль. Ни права
записи тренировочных фактов, ни операторские YDB/YC-записи не добавляются.

После нового OAuth-входа прежний черновик другого grant нельзя молча публиковать
с новым правом. Агент перечитывает текущую программу и создаёт проверенное
предложение под новым grant, сохраняя согласованное содержание и актуальную базу.
Личные payload остаются вне Git.

Обязательные проверки: прежние grants без повышения прав, запрет другому client,
владельцу и grant, отсутствие browser/session bypass, отзыв/истечение, неверные
редакция/digest/база, повтор и изменённый request ID, rollback при неподдерживаемом
представлении, сохранение истории и неизменность старого пути одобрения.
