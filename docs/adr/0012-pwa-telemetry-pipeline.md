# ADR-0012: Телеметрия PWA с доставкой по возможности через Gym API и Monium

- **Статус:** Принят
- **Дата:** 2026-10-20
- **Связанные решения:** [ADR-0002](0002-local-first-pwa.md), [ADR-0010](0010-ydb-serverless-cloud-functions.md), [ADR-0011](0011-github-actions-cicd.md)
- **Подробный проект:** [Телеметрия PWA](../observability.md#телеметрия-клиента-pwa-принятый-проект-adr-0012)

## Контекст

Gym — PWA с приоритетом работы без сети. Ошибки браузера, сбои записи IndexedDB, задержки синхронизации и состояние локальной очереди не всегда можно определить по серверным журналам. Прямая отправка из браузера в Monium раскрыла бы облачные учётные данные. В отличие от записей тренировок, диагностические данные допустимо терять.

## Решение

1. Реализовать небольшой **TelemetryClient** в PWA, собирающий только разрешённые и очищенные диагностические события ошибок, синхронизации, производительности, запуска приложения и service worker. Агрегировать счётчики локально.
2. **Никогда не отправлять телеметрию PWA напрямую в Monium.** Буферизовать её в ограниченной локальной диагностической очереди со сроком хранения, **отдельно от надёжной очереди исходящих операций тренировок**.
3. Отправлять небольшие пакеты аутентифицированным **`POST /api/v1/telemetry`** через Yandex API Gateway в Python Cloud Function, обычно примерно раз в минуту при активной работе с сетью. Допускать срочные попытки отправки по возможности при ошибках локального хранилища.
4. Необязательные `sendBeacon()`/`fetch keepalive` при уходе в фон; без гарантии доставки или подтверждения из браузера. Повторять только с ограничениями и сроком хранения; отбрасывать диагностику, а не рисковать надёжностью тренировок.
5. Сервер проверяет имена событий, версии, разрешённые поля, числовые границы, размер запроса, аутентификацию и ограничения частоты. Передаёт очищенные структурированные события и **фиксированные известные** агрегированные метрики/журналы в Yandex Monium по OTLP/HTTP с ограничением времени/ресурсов. Учётные данные остаются только на сервере; завершать отправку синхронно в пределах выполнения функции или использовать проверенный механизм провайдера.
6. Диагностические счётчики **приблизительны**, могут теряться, дублироваться или подделываться. Они не заменяют достоверные записи YDB или аудит и не определяют результаты тренировок или оплату.
7. Ни сбой телеметрии, ни задержка Monium не могут влиять на успешность уже сохранённого подхода, взаимодействие пользователя или надёжную синхронизацию тренировок. Показывать локальную очередь/последнее подтверждение (ACK) в диагностическом интерфейсе PWA; устройства без сети невидимы серверным метрикам до переподключения.
8. Не собирать исходные данные тренировок, идентификаторы пользователей как метки метрик, токены, полные тела запросов или произвольные сообщения/стеки исключений. Уведомления о конфиденциальности и управление сбором/согласием пользователей ещё предстоит спроектировать.

## Последствия

Одна недорогая бессерверная точка приёма телеметрии может обеспечивать клиентскую диагностику без постоянно работающего сборщика, сохраняя безопасность учётных данных и надёжность локального сохранения. События и пользовательские метрики требуют ограничений объёма, очистки и явных тестов. Избегать прямой записи метрик из браузера для каждого события.

## Остаётся открытым

Окончательная схема JSON телеметрии, квоты пакетов, политика согласия/отказа, ограничения аутентификации/cookie для beacon, стратегия пересылки и ограничения частоты. **Более широкий план наблюдаемости** (серверные журналы, платформенные панели, пороги мониторинга, оповещения) остаётся отдельным предложением и не утверждается этим ADR.
