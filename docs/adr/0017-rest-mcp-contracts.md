# ADR-0017: Формальные REST/MCP-контракты и канонизация Gym v1

- **Статус:** Принят пользователем 2026-10-26 командой «норм, завершаем этап» после рассмотрения P02.4.2
- **Дата:** 2026-10-26
- **Связано:** ADR-0001, ADR-0004, ADR-0011, ADR-0014, ADR-0015, ADR-0016

## Контекст

Вход/одобрение, снимки/очередь и управление явными целями через агента приняты. Для серверного каркаса и будущих клиентов нужны проверяемые формы запросов/ответов, маршруты, scopes, ошибки и одинаковые байты для повторов/digest. Наличие схем не заменяет проверку прав и транзакций.

## Решение

1. Хранить общие DTO JSON Schema 2020-12 и реестр операций/scopes/ошибок в `contracts/`; из них строить OpenAPI 3.1.2 и самодостаточные MCP tool schemas. Не поддерживать две независимые модели предметной операции.
2. Использовать `/api/v1`, закрытые поля, целые точные значения и явные nullable-поля канонических запросов. `fixed` — начальный тип правил; запись подходов доступна PWA, но не первоначальным MCP-инструментам.
3. Установить Gym canonical-json-v1: строгий JSON без дублей/нецелых чисел, ASCII-ключи в порядке, неизменный порядок массивов/Unicode-строк, UTF-8 и разделённые префиксами SHA-256 для операции, предложения и прочего идемпотентного запроса. Проверять одинаковые байты в Python/Node. Хеш не создаёт полномочий.
4. Связать публикацию с редакцией/base/digest и серверным одобрением, отделённым от OAuth. Основной путь — кнопка Gym публикует сразу; последующий MCP-вызов возвращает тот же результат. Не открывать агенту endpoint создания одобрения.
5. Разделить повторяемые ошибки, действия входа/разбора/обновления и окончательные квитанции. Курсоры/страницы выдаются в согласованной границе; совместимость schema 1 не истекает вместе с артефактами PWA.
6. Использовать MCP Streamable HTTP с коротким JSON-ответом в первом варианте; transport, negotiation и стандартные OAuth endpoints поручить проверенной библиотеке. Конкретная совместимость целевого клиента проверяется до подключения P10.2.
7. Проверять схемы, положительные/отрицательные примеры, привязки и канонизацию в CI без облачных прав. Авторизация, доступ к каталогу, атомарный приём YDB, cursor/approval races и настоящий Gateway остаются обязательной приёмкой реализации.

Полный контракт, размеры/defaults, маршруты и приёмка — в [contracts/README.md](../../contracts/README.md).

## Альтернативы и компромиссы

- Раздельные модели REST/MCP увеличивают риск несовпадения правил/прав; выбран общий DTO с разными transport envelopes.
- Разрешить неизвестные поля/молчаливое округление проще для части клиентов, но делает повторы/digest неоднозначными. Строгая v1 требует явной эволюции и поддержки старой очереди.
- Полноценная потоковая сессия MCP не нужна коротким предметным операциям первого пилота; JSON-ответ уменьшает требования к долгоживущим соединениям. Поддержку клиента и SDK нельзя предположить по одному manifest.
- Валидация ссылок/диапазонов может выполняться локально, но принадлежность данных/актуальность ревизии и одноразовость одобрения требуют серверного контекста/транзакции.

## Последствия

Появятся версионируемые контракты, генератор, тесты и отдельная проверка CI. Схемы ограничивают размеры представлений, не назначая тренировочные нагрузки. Реальное API/SDK/OAuth/YDB ещё предстоит реализовать; проект P02.4.2 принят, но проверка схем не означает готовности работающего сервера. Принятые ADR-0014–0016 не заменяются.
