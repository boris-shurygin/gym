# ADR-0011: CI/CD в GitHub Actions и развёртывание в Yandex Cloud

- **Статус:** Принят (процесс развёртывания и модель безопасности)
- **Дата:** 2026-10-20
- **Связанные решения:** [ADR-0009](0009-russian-hosting.md), [ADR-0010](0010-ydb-serverless-cloud-functions.md)
- **Подробный процесс:** [docs/ci-cd.md](../ci-cd.md)

## Контекст

Gym — небольшая PWA с приоритетом работы без сети, Python Cloud Functions и YDB Serverless в российском Yandex Cloud. Нужен воспроизводимый CI/CD без эксплуатации или аренды постоянного сервера CI. Репозиторий исходного кода `boris-shurygin/gym` публичный.

## Решения

1. **GitHub Actions** — оркестратор CI/CD на **стандартных временных исполнителях Ubuntu, предоставляемых GitHub**. Без выделенной/собственной инфраструктуры CI.
2. **Запросы на слияние (PR)** запускают, где применимо, линтеры/проверку типов, тесты интерфейса/браузера, серверные/модульные, контрактные, интеграционные тесты YDB и тесты миграций на синтетических данных и одноразовой YDB. У недоверенных PR нет промышленных учётных записей.
3. Слияние в **`main` автоматически развёртывает staging** после обязательных проверок и создаёт неизменяемые проверенные артефакты выпуска.
4. **Production требует ручного одобрения**, получает *те же* артефакты, что прошли staging; развёртывания и изменения схемы выполняются последовательно.
5. GitHub Actions использует **OIDC → Yandex Workload Identity Federation → краткоживущие учётные данные IAM**. Отдельные аккаунты staging/production с минимальными правами; никаких постоянных авторизованных ключей в коммитах или хранилищах GitHub.
6. GitHub оркестрирует процесс, но **промышленные миграции/заполнение данных YDB выполняются внутри Yandex Cloud** отдельным привилегированным заданием, а не при запросе/старте Cloud Function и не путём копирования промышленных данных на исполнители GitHub. Конкретный продукт для разового выполнения ещё не выбран.
7. Использовать совместимое развитие схемы: **расширение → развёртывание → заполнение данных → удаление устаревшего** (expand → deploy → backfill → contract). Старые кэшированные/работающие без сети клиенты PWA должны сохранять возможность синхронизации после выпуска. Откат кода не означает откат схемы БД.
8. Промышленный API Gateway указывает на **управляемый тег версии Cloud Function**, а не автоматически на последнюю; ресурсы статические, неизменяемые, с хешами в именах, а точки входа PWA/service worker публикуются последними.
9. Сбор журналов, счётчики, панели, оповещения и мониторинг отложены до отдельного обсуждения проекта.

## Оплата

Для публичных репозиториев **стандартные исполнители GitHub имеют бесплатные неограниченные месячные минуты**, что подтверждено документацией GitHub на 2026-10-20. **Увеличенные исполнители платные**, а хранилища артефактов/кэша имеют конечные лимиты. GitHub Free сейчас включает **500 МБ хранилища артефактов** (общего с GitHub Packages) и **10 ГБ кэша на репозиторий**. Если репозиторий станет приватным, текущий лимит GitHub Free — 2 000 минут исполнителей в месяц; стоимость нужно пересмотреть. Для текущего публичного репозитория и стандартных исполнителей в пределах лимитов хранения ожидаемый бюджет исполнителей GitHub Actions — **0 ₽**. Yandex Cloud оплачивается отдельно.

## Состояние и открытые подробности реализации

**Это утверждение архитектуры, а не развёртывание процессов автоматизации или облачных ресурсов.** Предстоит реализовать: файлы процессов, сервис запуска миграций, стратегию ревизий/восстановления схемы, настройки одобрения production, хранение артефактов выпусков, окно совместимости клиентов без сети и настройку учётных записей/доменов. См. [CI/CD](../ci-cd.md).
